A task is one change you want: fix a problem, add a feature, or improve a page. Describe the result
in your AI chat. The agent works out the steps and keeps the notes it needs to continue later.

```text Send to your agent
Add CSV export to the reports page. The file should include the date,
customer name, and total for each visible row.
Show me how to try it when it is ready.
```

<Tip>
  Give an example of a correct result. “Export the rows I can see” is easier to check than
  “make exports better.” If the task is large, ask the agent to break it into smaller parts.
</Tip>

## Talking about tasks

You do not need commands; these are the kinds of things you say:

| You say | The agent |
|---|---|
| *"Add CSV export to the reports."* | Classifies the work, files a task and starts it. |
| *"Note for later: we should cache the exchange rates."* | Files a task without starting it — no branch, nothing in the way. |
| *"What's in progress?"* | Lists the live tasks and what state each is in. |
| *"Continue the CSV export."* | Reads the task's workspace and picks up where it stopped. |
| *"Pause this, the export format isn't decided yet."* | Pauses the task with your reason, optionally stashing the uncommitted work. |
| *"Drop the caching task."* | Abandons it. |
| *"Close what's merged."* | Asks you about each merged task, then closes the ones you confirm. |

## What to do when the agent needs you

| The agent says | Your next step |
|---|---|
| It needs a product decision | Explain the outcome you want, or ask for options and a recommendation. |
| A design needs approval | Read it, ask for a plain-language explanation, then approve or request changes. |
| A check failed | Ask what failed and what the agent needs to fix it. |
| The change is ready | Try the result and ask what was checked and what is still missing. |
| It needs you to save or merge the work | Ask it to explain the remaining step, or [choose what it may do for you](/agent-ships). |

<Note>
  **Continuing tomorrow?** Open the same project and name the task: “Continue the CSV export.”
  If several tasks match, choose the one you mean. The task's notes help the agent pick up the work.
</Note>

<Accordion title="For developers: branches and task workspaces">


When the agent starts a task it creates:

- **a branch** of its own, cut from your main branch — or from an epic branch, when the task belongs
  to a specification that is released at once ([New project](/greenfield));
- **a workspace** in `.ai/workspace/tasks/<id>/` — the task description, analysis, plan or design,
  whatever its route needs. Workspaces are local to your machine and never committed: they are
  notes for the people and agents working on the task, not documentation.

Durable knowledge the task produces goes to `.ai/knowledge/` and is committed with the code.

Small work — a typo, a one-file fix that fits in one session — needs no workspace at all.

</Accordion>

## A task's states

| State | Meaning |
|---|---|
| **not started** | Filed, no branch yet. Filing something for next month costs nothing. |
| **active** | Being worked on. |
| **ready** | Checked: tests pass and the goal is met. Waiting to be merged. |
| **consolidated** | Closed: merged, and what it taught the project is recorded. |
| **abandoned** | Stopped for good. |

**Paused** is a mark on an active or ready task, not a state of its own: it says the work was
set aside, with a reason, and it comes back where it was.

## How a task ends

Every task ends with the question *what should the project remember?* — a new decision record, an
updated rule, or explicitly nothing. The agent records that answer **before** the commit, so the
knowledge travels in the same pull request as the code.

A merge alone does not close a task: a fix can still follow it. At the start of a session the agent
checks which of your tasks were merged, names each one and asks whether it can be closed. Nothing
is closed without your yes.

<Accordion title="How finished task notes are cleaned up">
What is left behind is cleaned up automatically. The workspace of a closed task is moved to a trash
folder, and deleted from there after a week. A task whose remote state cannot be determined keeps its
workspace. An abandoned task's workspace goes to the trash after two weeks, whatever its
remote state. The trigger is a Claude Code session hook
or a scheduler you choose ([Configuration](/configuration)).
</Accordion>

## Review findings

When a task is reviewed, each problem the review finds is written down in the task's workspace with a
severity:

| | Means | Stops the task |
|---|---|---|
| P0 | Breaks data or security, or goes against a rule or decision the project recorded | yes |
| P1 | Gives a wrong result on a path that will be used | yes |
| P2 | Worth fixing, but the code works without it | no |
| P3 | A small thing | no |

A P0 or P1 stops the task from being finished. Until it is resolved, the agent cannot mark the task
ready, record what the project should remember, or commit and open the pull request
([Letting the agent ship](/agent-ships)). A fix alone does not resolve it: the agent fixes the
problem, and a second review confirms the fix and closes the finding.

The other way out is to decide the problem does not need fixing — the review was wrong, or you accept
it. For a P0 or P1 that decision is yours: the agent shows you the finding and asks, and writes your
answer down with it. A P2 or P3 the agent may set aside on its own, with a reason.

To see where a task stands, ask *"what did the review find?"*, or run:

```bash
jig task findings <task-id>
```

`jig status` marks a task that is stopped this way with `blocking=<n>`.

### When the change moved after review

<Accordion title="For developers: review receipts and stale reviews">
A review ends by pinning what it looked at: the code, the approved design and its list of findings.
If any of them changes afterwards — a line of code edited, a finding closed by the agent that wrote
the code — the review no longer describes the change, and the task stops again for the same three
steps until the change is reviewed once more. Committing the reviewed change does not count as a
change; only its content does. The project's knowledge and specification files are not pinned: the
agent writes them after the review, as the last step of every task.

A task of the highest risk class (T4) cannot be finished without such a pinned review at all.

To see whether the review still holds, ask *"is the review still current?"*, or run
`jig task receipt <task-id> --check`. `jig status` marks a task whose review no longer holds with
`review=stale`.
</Accordion>

## Several agents at once

One checkout holds one piece of uncommitted work. When an agent is already working and you want to
start something else, say *"start the caching task in a separate worktree"*. The agent creates a
second working copy of the repository next to it (in `../<project>.worktrees/<id>` by default), cut
from the freshest main branch, and leaves the current work alone. Open a new agent session in that
folder — the agent tells you the path; some runtimes can switch there on their own.

An [autopilot run of a whole roadmap phase](/autopilot#running-a-whole-phase) does this for you:
it puts every task of a wave in its own worktree and gives each one its own agent.

Each worktree has its own branch and its own uncommitted changes; the task list in the original
checkout still shows every task and where it runs. A task's notes, plan and design stay in the
checkout where you filed it — a worktree only reaches them across, and the agent writes them
through Jig rather than by hand, so the task's date and the status page keep up wherever it works. Review and commit in the worktree as you would
anywhere. When the task is closed and its change has landed on its base — an epic branch included —
the worktree is removed, but only if it has no uncommitted changes and no lock. Worktrees you or your
agent created by hand are never removed.

### What a removed worktree takes with it

Git refuses to remove a worktree that holds changes it tracks or files it has never seen. The files
your project **ignores** are the exception: it deletes those without a word.

Jig adds one refusal of its own there. If an ignored folder holds a **separate Git repository** with
work that is nowhere else — not committed, or committed and on no remote — the worktree stays, and
the task is listed under "needs you" with the path, so you can go and push it. That covers the
expensive case, a repository you cloned or started inside a worktree whose commits exist only there.
An installed `node_modules` or a dependency pinned to a tag holds nothing back; if it did, a project
that installs anything would never be cleaned up at all.

**Everything else your project ignores still goes** — a `.env`, a local database, files you
generated by hand. This is not an oversight waiting to be fixed: nothing in a file says whether it
can be made again, and no rule can tell your `.env` from a folder your build wrote. What Jig does
instead is stop being silent about it. The line that records the removal in
`.ai/runtime/housekeeping.log` names the ignored paths that went with the worktree, so afterwards
the question "what was in there" has an answer.

So the rule for you is short: **do not leave in a worktree the only copy of something git does not
have.** To see in advance what one would lose, ask git inside it:

```bash
cd <the worktree folder>
git status --porcelain --ignored
```

Every line starting with `!!` is ignored, and ignored is what gets deleted. Copy out what you want
to keep, and push from inside any repository of its own. Running `git worktree remove` yourself is
exactly as dangerous as it always was — that half belongs to git, and no setting in Jig changes it.

## Seeing where things stand

`jig status` answers in the terminal. For a page you can keep open in your browser while the agent
works — or send to someone who does not use a terminal — ask the agent to *"open the status page"*,
or run:

```bash
jig status --open
```

The page shows what needs your answer, which tasks are running, and how far the project's plans
have progressed. Start with **Needs you**; each card tells you what to do next.

<Info>
  The page refreshes as Jig records changes. If it labels information as stale, ask the agent
  to refresh the status before relying on it.
</Info>

<Accordion title="For developers: status files, refresh behaviour, and all card types">
It writes one file, `.ai/runtime/status.html` in your project, prints its full path and opens it in
your browser. The same command works in Git Bash, in PowerShell and in the macOS or Linux terminal.
Where no browser can be opened — over SSH, for instance — the page is written anyway and the command
tells you where it is. `jig status --html` writes the page without opening it.

**The page keeps itself current.** Once it exists, every time the agent changes a task — starts it,
records a review finding, reaches a new stage, stops to ask you something — Jig redraws the file, and
the open page reloads itself every 10 seconds. You do not need to run anything again; the time at the
top says when it was last drawn. A reload keeps your place — the scroll position and the sections
you opened — and waits while you scroll, click or select text. To read without interruption, press
**Pause** in the bottom-right corner; **Resume** brings the page up to date at once. The pause lasts
until you close the tab. It is drawn from the checkout the tasks were filed in, which shows
every task started there, including those the agent went on to work on in a separate worktree:
starting a task in a worktree keeps its workspace where it was filed and links it across. Those
redraws only refresh a page that is already there: until you run `jig status --html` or `--open`,
nothing is written, and deleting `.ai/runtime/status.html` ends them — nothing recreates the page
until you ask for it again.

It answers four questions, in this order:

1. **Needs you.** Each card says what happened and, in one line, what to do:

   | Card | What to do |
   |---|---|
   | Autopilot stopped and is waiting for you | Answer the agent in that task's conversation; the card shows its question |
   | A design is waiting for your decision | Read the design the agent showed you, then approve it or say what to change |
   | A design changed after you approved it | Read what changed and approve it again |
   | Ready for your step in git | Commit, push or open the pull request — whichever step the agent may not take in your project |
   | A pull request is waiting for review or merge | Review it and merge it; the link opens it. Jig merges one itself only at `agent.git: merge`, once CI passed |
   | Merged: the task can be closed | Tell the agent to close the task |
   | The work landed on a different branch than planned, the pull request was closed without merging, a worktree was kept | Look at it; only you can say what happens next |
   | Knowledge is waiting for your decision | Ask the agent *"what's proposed?"* |

   When there is nothing to do, it says *Nothing needs you right now*.
2. **Running now.** Every task in progress: its class, status, the branch it lands on, the worktree
   it runs in, whether its review still holds (current, stale, or none yet — and whether a T4 task
   still needs one), and each finding that stops it. For a task on autopilot it also shows the stage
   it is in, for how long, and how many of its two fixing attempts it used. Paused tasks are folded
   away below.
3. **Specifications.** How far every roadmap has got, phase by phase. For a specification built on
   its own branch, the progress is read from that branch as your copy of it last saw it.
4. **Details.** The counts at a glance, and the complete `jig status` text, folded away at the bottom.

**Why some data is marked stale.** Whether a pull request is open or merged comes from housekeeping,
which asks GitHub or GitLab once a day when an agent session starts. When its last run is older than
that, or GitHub/GitLab did not answer, the page says *stale*; run `jig housekeeping` to update it. A
pull request the agent opened itself appears at once, with its link. The knowledge counts come from
the last full `jig status` and show their time too.

To open the file by hand, double-click `status.html` in your file manager — on Windows, in File
Explorer, open your project folder, then `.ai`, then `runtime`; on macOS, Finder hides folders whose
name starts with a dot until you press Cmd+Shift+. (period). From a terminal:

| System | Command |
|---|---|
| Windows (Git Bash) | `start .ai/runtime/status.html` |
| Windows (PowerShell) | `Invoke-Item .ai\runtime\status.html` |
| macOS | `open .ai/runtime/status.html` |
| Linux | `xdg-open .ai/runtime/status.html` |

The page is a single file with nothing to download; its one small built-in script only reloads it
and keeps your place. It opens in any browser, offline, and follows your system's light or dark
theme; with JavaScript turned off it still reloads every 10 seconds, without keeping your place. Nothing but the page and the counts it reuses is
written, both in `.ai/runtime/`, and neither is ever committed.
</Accordion>

## When the work turns out bigger

A task starts with a class the agent chose from the risk it saw. When the work turns out bigger — a
"local fix" that touches an interface other parts depend on — the agent re-classifies it and runs
the stages the new class requires, including your approval where the new route has a human gate.
Risk sets the floor: a one-line change to authentication is never trivial.

## Who commits

By default the agent does not commit: a finished task waits in your working tree, and you review the
diff and commit it. One line in your own `.ai/config.local.yaml` — `agent.git: pr` — lets the agent
commit, push and open the pull request instead; only `agent.git: merge` also merges, once CI passed.
[Letting the agent ship](/agent-ships) explains the levels and what happens at the end of a task.
