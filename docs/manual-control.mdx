title: "Manual control"
description: "Inspect tasks, manage their lifecycle, resolve context, and run checks from the terminal."
---

Use these commands when you want to inspect or manage Jig yourself. Run them from your project
folder. The examples use `jig` on your `PATH`; `.ai/scripts/jig` runs the project's installed copy
explicitly. In PowerShell, use `.ai\scripts\jig.cmd` for that local copy.

<Info>
  **Commands keep the records; the agent does the work.** Creating a task in the terminal does
  not start an AI session or write code. Return to your agent and ask it to continue the named task.
</Info>

## Inspect before changing anything

```bash
jig task list
jig task current
jig status
jig doctor
```

`task list` shows the tasks, and says how many are archived (`jig task list --status archived` lists them); `task current` looks for the task on this branch. When several match,
choose an explicit ID. `status` summarizes the project and `doctor` checks its setup.
A script can read the same task list as JSON with `jig task list --json`, the specs with
`jig spec list --json`, the queue with `jig queue list --json`, and what needs you with
`jig status --json`; see
[Reading Jig as data](/reading-jig-as-data).

To create the browser status file without opening a browser:

```bash
jig status --html
```

Or use `jig status --open` to create and open it.
[Read about the status page](/working-with-tasks#seeing-where-things-stand).

## File a task, then start it

For this example, assume a contained change already classified as T1. Use the appropriate
[risk class](/concepts#risk-classes-and-routes) for your actual work.

```bash
jig task new booking-message --class T1
jig task show booking-message
```

Fill in `.ai/workspace/tasks/booking-message/task.md`: the goal, scope, and what a correct result
looks like. Filing the task does not switch branches.

To give the goal as you file it, pass it as one line; it becomes the paragraph under `## Goal`:

```bash
jig task new booking-form --class T1 --goal "Guests can book a table"
```

To start from a brief you already wrote, pass `--from <file>` instead.

<Warning>
  Start from a repository with a commit and no uncommitted tracked changes. If other work is in
  progress, pause its task or use a separate worktree; do not bundle it into this task's commit.
</Warning>

Begin work separately:

```bash
jig task start booking-message
```

By default, this switches to a task branch from the project's configured base. For a separate
working copy, use `jig task start booking-message --worktree` instead, then work in the directory
it prints. Tasks linked to a spec with an open epic start from that epic.

A new worktree also gets whatever `vendor/`, `node_modules/` or `.env` your project's profiles (and
[`worktree.carry`](/configuration#git-and-branches)) declare, and links to the folders
`worktree.share` names — see
[carrying state into a worktree](/working-with-tasks#several-agents-at-once). Add `--no-bootstrap`
to skip that for this run, or repeat it later with `jig task bootstrap booking-message`. Then your
project's own [`worktree.setup`](/working-with-tasks#finishing-a-worktree-with-your-own-command)
runs, if it has one.

`--share packages` gives this one task the links to `packages/` that `worktree.share` gives every
task; `jig task bootstrap booking-message --share packages` adds them to a task already running.
See [sharing for one task](/working-with-tasks#sharing-for-one-task).

## Pause and resume

```bash
jig task pause booking-message --reason "Waiting for the final wording"
jig task resume booking-message
```

Add `--stash` to the pause command when you also need to put uncommitted work aside. Resume reports
what changed while the task was paused. Read that report before continuing.

Resume runs in any checkout, unless the pause stashed work: then run it where the task's branch is
checked out (its worktree, if it has one), because that is where the stash is applied.

When an agent is working on the task, on autopilot or in an ordinary session, ask it to pause
instead:

```bash
jig queue request booking-message pause --reason "Need to check the copy first"
jig queue cancel booking-message pause
```

The agent finishes the stage it is on, pauses the task instead of starting the next one, and stops.
An autopilot run checks when it enters its next stage; any agent checks when the next stage reads
its context with `jig context resolve --task <id> --stage <stage>`, the first step of every stage
skill. A stage without a skill of its own, such as a plan, reads none, so the request then waits for
the stage after it. The request waits until then, or until you cancel it. Resume as above, and start
a new session to continue.

## Archive and unarchive

```bash
jig task archive booking-message
jig task list --status archived
jig task unarchive booking-message
```

An archived task leaves the lists but is not deleted: its notes stay in `.ai/workspace/tasks/`, and
its branch, worktree and pull request are not touched. You can archive an active, ready or abandoned
task. Housekeeping does the same for an abandoned task after `housekeeping.abandoned_ttl` and for an
idle one after `housekeeping.stale_after`. `unarchive` returns the task to the status it had.

## Merge a task into another

```bash
jig task merge booking-message --into booking-notifications
jig task merge booking-message --into booking-notifications --partial
```

When one task turns out to do another's work, merge it. The documents of `booking-message` are
copied, not moved, to `absorbed/booking-message/` in the receiving task's notes, and the receiver's
`task.md` gets a section that names them. Without `--partial` the absorbed task is archived (reason
`absorbed`) and anything in the queue that waited on it waits on the receiver instead; `jig task
unarchive` brings it back. With `--partial` the task stays open and both sides note the overlap;
the queue is left alone. The receiving task must be active or ready, and a merge that would make the
queue wait in a circle is refused before anything changes.

Jig does not touch your tracker. When the receiving task ships, its commit and pull request name the
absorbed tasks' issues in an `Absorbs:` line, so the tracker's own integration can link or close them.

## Order the work

```bash
jig queue set booking-message --priority 1
jig queue move booking-message --before booking-form
jig queue depend booking-message --on booking-form --reason "The message quotes the form's fields"
jig queue
```

The queue keeps the priority, order and dependencies of your tasks and epics, one queue for the
whole project, outside git. Priority runs from `0` (most urgent) to `5`, and each number means
one thing, so that you and your agent set "bugs first" the same way:

| Priority | When |
|---|---|
| `0` | Something is broken or dangerous: data loss, a destructive operation, an install that fails |
| `1` | A bug a user meets |
| `2` | Not a bug, but it stops a user doing their own work |
| `3` | Friction: the work gets done, with more effort than it should take |
| `4` | An improvement or a new capability |
| `5` | Some day |

`--priority none` takes the priority away. A move places one item
before or after another, or with `--top` and `--bottom` at an end; an epic (`epic:<spec-id>`) is
ordered beside tasks, and the tasks built on it are ordered within it. A dependency always says why.
`jig queue remove` takes an item out, and `jig queue undepend` drops a dependency. A program
reads the queue with `jig queue list --json` ([Reading Jig as data](/reading-jig-as-data#the-queue)).

To ask which task to take next, run `jig queue next`. It answers from the queue and from what Jig
already knows, over the network never, and changes nothing:

```text
next: task:booking-form — 1 of 3 on the top level, priority 1, started
  task:booking-message waits for task:booking-form: unknown — jig housekeeping
not queued: 1 task — jig queue set <id> --priority <p>
```

Only a task that is `active` and not paused is advised, and one waits while anything it depends
on, or the epic it is built on depends on, is not finished. A task is finished when it is closed
or `jig housekeeping` saw its pull request merged; an epic when its branch has landed. Among the
tasks that do not wait the lowest priority number goes first, with a task without one last; at the
same priority a task already started goes before one not started; after that comes the place in
the queue, a task on an epic taking its epic's place. When no task can be taken it says why:
every queued task waits for a dependency, is paused, or there is none. A wait that can never end
(`broken`: the task it waits for was abandoned, archived or is gone) comes with the command that drops it;
one Jig cannot tell (`unknown`) with the one that may find out. The last line counts the active
tasks that are not in the queue. `jig queue next --json` gives the same answer to a program
([Reading Jig as data](/reading-jig-as-data#which-task-is-next)).

`jig status` shows each queued task's place on its task line — `queue=2/5` is second of five on its
level (the top, or the epic it is built on), `priority=1` its priority — with what it waits for, and
a pause asked of it with its age, on the lines under it:

```text
task booking-message class=T2 status=active queue=2/5 priority=1
  waits for task:booking-form: The message quotes the form's fields
  pause requested 12 min ago: need the laptop
```

Once the project has a queue, `jig status` also prints the first line `jig queue next` gives, after
the task lines, so the answer is where you already look (the status page shows it as "Next task"):

```text
task booking-form class=T2 status=active queue=1/2 priority=1
task booking-message class=T2 status=active queue=2/2 priority=2
next: task:booking-form — 1 of 2 on the top level, priority 1, not started
current task: none
```

When nothing can be taken the line reads `next: none — ` and the reason; `jig queue next` has the
lines under it. `jig status` only reads that answer, it does not work it out again.

`jig context --task <id>` gives the agent working on the task the same facts as `queue:` lines.
Without a queue, none of this appears and the output looks as it always has.

## Inspect the change and its review

```bash
jig task changes booking-message --base main
jig task findings booking-message
jig task receipt booking-message --check
jig task receipt booking-message --since-review
```

Replace `main` with the task's actual base from `jig task show booking-message`. The change inventory
includes committed and local changes; it does not prove that every change belongs to this task.
Findings and the receipt tell you what was reviewed and whether that review still matches the work.
A missing receipt can be expected before review or for a task whose route does not require one.
When the receipt is stale, `--since-review` shows what changed since the review, and whether a repeat
review may read only that (`narrow`) or must read everything (`full`, with the reason).

## Ask which knowledge applies

```bash
jig context resolve --task booking-message --stage analyze --catalog
```

Read the required documents. The catalog lists other potentially useful documents; select those
with `--ids` when needed. For an investigation without a task, pass explicit file selectors:

```bash
jig context resolve --no-task --files README.md --catalog
```

Replace `README.md` with the actual paths you are investigating. To record documents you have
actually read, use `jig context acknowledge`; `jig context guard` checks that record.
[How context works](/under-the-hood#knowledge-and-what-an-agent-reads).

## Run the project's checks

```bash
jig verify --explain
jig verify --changed
jig knowledge check
```

`--explain` previews each check as full, filtered, skipped or conditional without running
the checks or waiting for another verification. It uses the same scope choice as a plain
`jig verify`; combine it with `--changed`, `--full`, `--base` or `--profile` to preview
those choices. Conditional means a tool such as Go or Jest would have to inspect the
project before the final set is known, so a full run remains possible. The preview is
not verification: exit 0 means a plan was printed, exit 2 means an installed profile
could not explain its plan, and exit 1 means the preview failed.

`--changed` requests checks for the changed files. Each profile says whether it narrowed its work
or ran the full check. A plain `jig verify` follows the project's `verify.full_run` setting.
[Configure verification](/configuration#verification).

<Warning>
  **Skipped is not passed.** Read the report even when the command exits successfully. Missing
  tools or dependencies can leave checks unrun.
</Warning>

## Preview a personal setting

This example previews letting the agent commit, push, and open pull requests:

```bash
jig config set agent.git pr --local --dry-run
```

To apply it, remove `--dry-run`. To return to the default, use:

```bash
jig config unset agent.git --local
```

Personal settings live in the ignored `.ai/config.local.yaml`.
[Compare the permission levels](/agent-ships#choose-how-far-it-goes) before changing one.

## Finish through the workflow

Ask the agent to verify the result and record what the project should remember before shipping it.
`jig task ship` follows your personal permissions and checks the task's completion records.
After the change lands, confirm whether the task can close.

<Tip>
  `jig help` lists the full command surface. Use [Skills](/skills) for the agent procedures,
  [Configuration](/configuration) for settings, and [Under the hood](/under-the-hood) for boundaries
  and side effects.
</Tip>
