This page says what is coming and in which order. It carries no dates: what is written here is the
order the work is taken in, and that is the only thing anyone can promise honestly about software
written a task at a time.

The order is not a ranking of how interesting the work is. It is what a mistake costs the person
who meets it. Things that take work away from you come first, however small they are to fix. Things
that tell you something untrue about the state of your project come next, because you cannot act on
a report you cannot trust. Things that merely cost time come after those. New capabilities come
last, and wait for all of it.

[Known issues](/known-issues) describes the faults themselves — what you see, what it costs, and
what to do instead until each one is fixed.

## First: what takes work away from you

Nothing known today. When something is found, it goes here, ahead of everything below.

## Then: what tells you something untrue

**A green verify must belong to the files it checked.** A review already records what it read, and
says so when the code moves on underneath it. A verify result does not: once the checks pass, the
task reads as verified even if files changed afterwards, and a change can be shipped under a result
that was earned by a different tree. The result gets pinned to its inputs, the way the review is,
and a moved tree asks for a new run.

**A resume whose stash conflicted must tell the truth.** It tells you to resolve the conflict and run
it again, and the retry can never succeed: it applies the same stash a second time. The resume will
recognise the stash it already applied and end the pause
([known issue](/known-issues#a-resume-whose-stash-conflicted-can-never-be-retried)).

## Then: what costs you time

**A stopped worktree setup must stop on Windows too.** Under Git Bash, a `worktree.setup` stopped at
its timeout can leave what it started running
([known issue](/known-issues#under-git-bash-a-stopped-worktree-setup-may-leave-its-processes-running)).

**A second review round must not open a new front.** A repeat review already reads only what
changed since the review (0.30.0). What is left: a blocker that appears only in the second round
goes to you instead of starting a third. Each extra round is where the time goes, and this bounds
them.

**An uncertain finding gets a second opinion before anyone fixes it.** A review finding the reviewer
is not sure of is handed to a fresh agent that has not seen the reasoning behind it, and is kept
only if that agent confirms it. A wrong finding then costs one check instead of a round of fixes.

## After that: new capabilities

**Planning that lives in Jig.** Jig can be read by a program (0.29.0), planned with (0.31.0) and
asked what to take next (0.32.0): a queue holds the priority, order and dependencies of tasks and
epics, a running task can be asked to pause, and `jig queue next` advises the next task from them.
What is left: a way for `jig init` to tell an installed Jig UI about a new project.

**Project hooks.** A way for a project to bind its own rules and its own checks to stages of the
route, so that what a project insists on is asked at the stage it belongs to rather than remembered.

**A bug fix starts from the failure.** For a task that fixes a defect, the route asks for the
failure first — reproduced by a test or a written check — then the fix, then the same check again.

**Defects leave a record, and records become rules.** A fixed defect leaves a short structured note:
the cause, the kind of mistake, the files. A skill reads many of them and proposes project rules
for what keeps recurring; a person accepts or rejects each one, as with any proposed knowledge. This
needs a decision recorded first, because it is a new kind of record.

**Knowledge documents that name each other.** An ADR that replaces another, a document that affects
another — written as typed links and checked mechanically, so that a replaced decision cannot stay
quietly in force.

Beyond that, ideas with no start date: a link from each requirement in a specification to the check
that proves it; accepting a known failure with a reason and an end date rather than switching the
check off; a separate security pass for the riskiest tasks; noticing an unattended run that has
gone silent; knowledge shared between several repositories; and knowledge that lives in a section
of an existing file rather than a whole one.

## Beside Jig: Jig UI

[Jig UI](https://github.com/fapost-lab/jig-ui) is a separate, optional project, in the making: a
local page with a board across all your Jig projects, where tasks and epics are ordered and
prioritised and new tasks are filed. It reads and changes your projects only through Jig's own
commands and contracts — the JSON form described in [Reading Jig as data](/reading-jig-as-data), and the planning described above — so Jig
works exactly as it does without it. What its next phase needs from Jig — the queue, pause
requests and filing a task from a program — is in 0.31.0, so that phase can start on it; resuming a
paused task from a program is in 0.35.0. Its plans
live in its own repository, and its documentation at [jig-ui.fapost.in](https://jig-ui.fapost.in).
