Start with the project you already have. The agent learns how it works, records the important
rules, and uses those notes when making changes.

## 1. Connect Jig to the project

Follow [installation and setup](/install), using your existing project folder. Review and save
what setup adds before starting a task.

<Warning>
  Existing `AGENTS.md` and `CLAUDE.md` files are preserved. If the agent does not recognize Jig,
  ask it to “connect Jig to my AGENTS.md” and review the section it proposes to add. Keep the
  `<!-- jig:begin -->` and `<!-- jig:end -->` lines it puts around that section: with them,
  `jig upgrade` keeps the section current; without them, it stays at today's version forever.
</Warning>

## 2. Check the agent's understanding

```text Send to your agent
Set up Jig for this project. Explain what the project does,
its main parts, and the rules changes must follow.
Use the existing code and documentation, and ask me about anything unclear.
```

The agent writes project notes and shows them to you. Correct anything it misunderstood before
asking it to build on that understanding.

**You should have:** an agreed description of the project, the terms it uses, and its rules.
If you already completed this during installation, continue to the next step.

<Accordion title="For developers: what the agent reads and writes">
  `jig-init` reads manifests, entry points, the directory layout, and existing documents. It writes
  `GLOSSARY.md`, `ARCHITECTURE.md`, and `RULES.md` under `.ai/knowledge/`, and validates them with
  `jig knowledge check`. It asks about ambiguous boundaries and terms rather than inventing them.

  Setup detects verification profiles from the project's manifests. Those profiles run your own
  tools; install the project's dependencies before expecting the checks to run.
</Accordion>

## 3. Bring in your existing rules

If your team already keeps architecture notes, coding conventions, or instructions for other AI
tools, ask the agent to use them:

```text Send to your agent
Adopt our existing docs into Jig. Show me which documents contain rules,
where they disagree, and what you propose to use.
```

Then say **“Review the proposals.”** The agent shows what it wants future sessions to follow.
Accept what is right, ask for corrections, or reject it. Ordinary user guides do not need to become
rules for the agent.

<Info>
  Proposed rules wait for your decision. They do not become instructions for future tasks just
  because the agent wrote them down. You can skip this step if you have no additional rules to adopt.
</Info>

<Accordion title="For developers: links, copies, conflicts, and acceptance">
This is the step that makes Jig fit a project instead of sitting beside it. Without it you would
have two sets of rules — yours and a new one — drifting apart.

**You say:** *"Map the project's knowledge"*, or *"adopt our existing docs into Jig"*.

**The agent does:** first takes an inventory of what the repository already holds:

- instruction files of AI tools — `.cursorrules`, `.cursor/rules/`, `.github/copilot-instructions.md`,
  your own `CLAUDE.md` — with their Git state;
- Markdown documents with their size and Git state — conventions, decision records, architecture
  notes;
- folders it did not open (ignored ones such as `node_modules/`), named so you know what was not
  looked at.

Then it decides, document by document, what is a rule and what is not:

| What it finds | What it does |
|---|---|
| A rule document Git tracks — conventions, your ADRs, an architecture note | **Links it in place.** A small pointer is created in `.ai/knowledge/sources/`; your file stays where it is and stays the one to edit. |
| Another AI tool's instruction file | Links it the same way, unless every runtime you use already loads it by itself. |
| A rule file Git does not track, or ignores | Offers to **copy** it — after showing it to you whole, because it may be a private note. The copy is scanned for things that look like secrets; when something does, it names the line, never the value, and stops until you have looked. The scan catches the obvious only. The original is never changed or deleted. |
| A README, changelog, API reference, guide for people | Skips it and says so. |
| The same rule written in two places, or two places that disagree | Lists them side by side in its report, with how it would reconcile them — and settles nothing itself. Your existing rules keep their authority until you decide. |

Where the code shows parts the documents do not describe, it proposes domain knowledge for them
too — each statement marked as observed, inferred or proposed.

**Under the hood:** the `jig-map` skill; it works inside a task, so the agent files one first. Every
linked, copied or new document is created as **proposed**. A proposed document is in the
repository and in the diff, but no agent receives it: `jig context` resolves only accepted
knowledge. `jig status` counts what is waiting on its `proposals:` line.

**Where you are needed:** everything. The agent shows its report and each proposed document — for a
linked document, its path and size, and the file itself on request — and waits.

### Accepting the proposed rules

**You say:** *"Review the proposals."*

**The agent does:** numbers the waiting documents, shows each one with what it claims in a sentence
and what accepting it causes — which files it would apply to, and how much every future agent
touching those files would have to read. You answer with numbers, "all", or a domain name; it never
asks you to type an id.

**Under the hood:** the `jig-accept` skill; `jig knowledge accept` and `jig knowledge reject`.
Rejecting records the decision on the document instead of deleting it, so nobody proposes the same
thing again.

**Where you are needed:** this is your decision alone. The agent says which proposals it is least
sure of.

**What happens after:** an accepted document reaches every agent whose work it applies to. A
document tied to parts of the code arrives when those files are touched. A project-wide one —
your team's ADRs, general conventions — is listed to every agent as a one-line entry it can open.
Later, when someone edits a linked file, `jig status` reports it on its `sources changed:` line
until a human has looked at the change; agents read the new text meanwhile.

<Note>
  **What adoption does not do yet.** A rule that lives in a *section* of a larger file — the
  "Development" part of a README — can only be linked with the whole file, or written into
  `RULES.md` by `jig-init` as a copy. A new decision in a project with its own ADR folder follows
  that folder's numbering only when the agent writes it at the end of a task. And nothing migrates
  your documents into Jig's own structure: they stay yours, where they are.
</Note>

</Accordion>

## 4. Start with a change you can check

```text Send to your agent
Add a message when the class schedule is empty.
It should say "No classes yet — check back soon."
Use Jig for this task and show me how to test the result.
```

The agent chooses the steps the work needs, makes the change, and runs the available checks.
For larger work it may first show a plan or ask you to approve a design.

**Before finishing:** try the changed behaviour and ask what was tested, what was skipped, and
whether anything still needs your attention.

<Tip>
  A small first task helps you see how Jig fits your project before handing over a large feature.
</Tip>
