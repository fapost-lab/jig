This page lists faults in Jig that you can run into without reading its source code. Each entry
says what you will see, what it can cost you, and what to do instead.

<Note>
  **What this page describes.** Jig as it stands today — the code the next release is cut from.
  It is not a report about one installed version, so your copy may behave differently.
  The [changelog](/changelog) is where each release records what changed.
</Note>

**This is not the page for "something went wrong".** If a command refused, a setting did not take,
or your agent ignored Jig, start with [Troubleshooting](/troubleshooting) — those are problems with
an answer today. An entry below stays here until the fault is actually fixed, and it is removed in
the same change that fixes it.

The page is not a list of everything Jig could do better, and it is not a copy of Jig's to-do list.
Work already under way is left out. For the order these are being fixed in, and what comes after
them, see [What's next](/roadmap).

## The Windows installer refuses a drive root that is already your repository

{/* closed by jig task: installer-allows-a-drive-root-that-is-a-repository — remove this entry in the PR that merges the fix */}

The installer refuses to set up a project in the root of a drive or a network share, because a
repository there would take in everything on it. It refuses that folder even when it already *is*
the top of an existing repository — a `subst` drive pointed at a project, a volume kept for one
project, a `\\server\share` holding one — where nothing of the kind would happen. 0.16.0 accepted
it. With `-Yes` or `-Project` the installer exits with an error; asked interactively, it wants
another folder.

It costs you the last step, not the install: Jig itself is installed and working, and only the
setup of the project stopped.

**What to do instead.** Set the project up yourself, from that folder:

```powershell
cd P:\
jig init --session-hook
```

`--session-hook` adds the Claude Code session hook the installer would have added; leave it out if
you ran the installer with `-NoSessionHook`.

## A Jig project cloned on Windows stops taking upgrades

{/* closed by jig task: manifest-survives-a-windows-clone — remove this entry in the PR that merges the fix */}

Git for Windows, with its default settings, writes text files with Windows line endings whenever
it checks a project out. Jig pins its own line endings for its scripts only, so a fresh checkout
of a Jig project — a clone, and on the same machine a task worktree
(`jig task start --worktree`) — gets the rest of Jig's files that way, `.ai/manifest` among them.
Jig then cannot read its own manifest. `jig upgrade --dry-run` reports almost every framework file
as a conflict, and `jig upgrade` places none of them; measured on a project of 97 framework files:

```text
jig upgrade: 0 placed, 26 kept, 71 conflict(s); manifest unchanged (dry run)
```

The checkout where Jig was installed is not affected, so this reaches whoever joins the project
on Windows. It costs you updates: that copy stops receiving Jig's changes, and `jig status` there
reports `drift: 0 modified`, so nothing points at the cause.

**What to do instead.** In the project, pin the line endings of the rest of Jig's files. Add these
lines to `.gitattributes` and commit them:

```text
.ai/** text eol=lf
.claude/skills/** text eol=lf
.codex/skills/** text eol=lf
```

A clone or a worktree made after that commit upgrades normally. One made before it keeps the
files it was given: clone again, or make the worktree again. If you already ran `jig upgrade` in
such a copy, it rewrote `.ai/manifest` without fixing anything; do not commit that change —
`git checkout .ai/manifest` puts the file back.

## Removing a task worktree by hand has no protection

{/* closed by jig task: worktree-share — remove this entry in the PR that merges the fix */}

`worktree.carry` copies ignored state into a task worktree, and a path you name can itself contain
a Git repository — a `packages/` folder of local clones, say. Jig's own cleanup handles this: it
asks every Git repository inside a worktree whether it holds work that exists nowhere else, and
keeps the worktree instead of removing it when one does.

Nothing extends that to `git worktree remove` typed by a person. That command is Git's, it deletes
ignored files without asking, and Jig does not change its behaviour. So a commit you made inside a
carried clone — one that lives only there, never pushed, never in the main checkout — goes with
the folder, and Git's own reflog cannot help you because the repository that held it is gone.

Separately: `carry` accepts a path with a `.git` inside it without a word of warning, so nothing
tells you at the moment you configure it that this is the case you are setting up.

**What to do instead.** Remove task worktrees through Jig rather than by hand, and let its cleanup
answer the question. Before removing one any other way, push what is inside the carried
repositories, or check them:

```bash
git -C <worktree>/<carried path> status --short
git -C <worktree>/<carried path> log --branches --not --remotes --oneline
```

The second command lists commits that exist in that clone and nowhere else. If it prints anything,
that work is what the removal would take. There is no Jig setting that makes a carried path
shared rather than copied; a project that needs one checkout of a package shared across worktrees
has no option today but to leave it out of `carry` and accept that the worktree cannot build.

## Autopilot can close a task whose work was never merged

{/* closed by jig task: autopilot-end-closes-unmerged-task — remove this entry in the PR that merges the fix */}

`jig task autopilot <id> end` marks the task consolidated without asking whether its pull request
was merged. At `agent.git: pr` the run ends exactly there — an open pull request, waiting for you —
and the task is closed in the same breath.

A closed task leaves `jig status`. So the pull request nobody merged becomes invisible at the one
moment it needs watching: the agent that opened it does not list it any more, and neither does
anyone else opening the project afterwards. Nothing is lost, but it is easy to forget for as long
as you do not happen to look at the forge.

Closing by hand is no safer here. `jig task set <id> status consolidated` refuses only while the
knowledge decision is unrecorded, and by the end of a route that decision has been made — so the
manual path allows the same close. Neither writer asks whether the change landed.

**What to do instead.** After an autopilot run ends, look at the pull request it hands back and
merge it yourself. To find tasks in this state later, list the closed ones and check their
branches:

```bash
jig task list --all
```

A task marked `consolidated` whose branch still exists unmerged on the forge is one of these; it
can be reopened with `jig task set <id> status ready`.

## Housekeeping can leave `git fetch` hung, and the count grows

{/* closed by jig task: fetch-never-waits-for-a-prompt — remove this entry in the PR that merges the fix */}

Housekeeping fetches from your remote without telling Git that no one is at the keyboard. Against a
remote that asks for credentials — an HTTPS remote with no credential helper, an SSH key with a
passphrase, a host whose fingerprint is not known yet — the fetch stops and waits for an answer
that will never be typed.

It then gets worse on its own. Housekeeping records that it ran only at the *end*, so the run that
is stuck waiting never records anything. Every new session therefore decides that housekeeping has
not run, and starts another one. The hung processes accumulate, one per session, for as long as the
remote keeps asking.

**What to do instead.** Make the remote answer without a prompt, which fixes the cause rather than
the symptom: store credentials in a helper, load your key into an agent, or accept the host key
once by fetching manually. To see whether you have any of these, and clear them:

```bash
ps ax | grep '[g]it fetch'
```

They are safe to kill — a fetch writes nothing until it completes. If you cannot make the remote
non-interactive, turn the fetch off with `housekeeping.fetch: false` in
`.ai/config.local.yaml`, and fetch by hand.

## `jig context` takes tens of seconds

{/* closed by jig task: knowledge-costs-one-walk — remove this entry in the PR that merges the fix */}

Resolving which knowledge documents apply to a set of files walks the whole working tree once for
every path pattern in your knowledge, rather than once in total. Measured on a project with 83
documents: 291 tree walks, about 8,500 processes, and 30 to 39 seconds for a single
`jig knowledge check`. `jig context` takes around ten seconds and the guard recomputes it from
scratch, so one ordinary task route pays roughly twenty seconds four times over.

It grows with the repository. On a project of twenty thousand files this is minutes, not seconds —
and the larger the project, the more the progressive loading of knowledge is worth, which is
exactly where it becomes too slow to keep.

**What to do instead.** Nothing you configure changes the cost. What you can do is not pay it
needlessly: ask for context once per stage and keep the answer, rather than resolving it again for
each file you touch, and pass the files you actually changed:

```bash
jig context --files <the files this change touches>
```

Keeping `.ai/knowledge/` to documents that earn their place helps proportionally, since the cost
is per path pattern. If your agent has started skipping `jig context` because it is slow, that is
this fault, not a preference — the fix is coming rather than the feature being optional.

## A task that has already started cannot be moved into a worktree

{/* closed by jig task: task-move-to-worktree — remove this entry in the PR that merges the fix */}

You can ask for a worktree when a task starts. You cannot ask for one afterwards:

```text
$ jig task start my-task --worktree
jig: error: task start: already started on task/my-task
```

The refusal is about starting a task twice, and it is raised before the request for a worktree is
looked at — so there is no way to say "this task has begun, now give it a place of its own". You
meet this exactly when it would help most: something else has come up, and the task you started is
in the way.

**What to do instead.** Move the *other* work, not this one. A task can have a worktree from the
moment it starts, so give the new task one:

```text Send to your agent
Start the next task in its own worktree.
```

If it really has to be this task that moves, that is Git's job rather than Jig's, and it is worth
doing with your agent while you watch: the branch has to be checked out in the new folder and let
go of by the old one.

## After a spec session, `jig task start` refuses and does not say how to go on

{/* closed by jig task: idea-leaves-a-tree-task-start-refuses — remove this entry in the PR that merges the fix */}

Working on a spec with the `jig-idea` skill changes files under `.ai/specs/` that are already
committed — in a second session on the same spec, or when the skill files a phase's tasks and
writes their names into the roadmap. The next natural step, starting one of those tasks, then
refuses:

```text
jig: error: task start: uncommitted changes in the working tree; commit them, or pause the task that owns them with --stash, or start it in its own worktree: `jig task start my-task --worktree`
```

The changes it refuses on are the spec your session just wrote, and the refusal does not name the
command that ships a spec. The `jig-task` skill tells your agent never to work around this
refusal, so the agent stops and comes back to you. A spec that was never committed does not
trigger it.

**What to do instead.** Ship the spec first, then start the task:

```bash
git add .ai/specs/<spec>
jig spec ship <spec> --message-file <file>
jig task start <task>
```

`jig spec ship` goes as far as your [Git permissions](/agent-ships#specs-and-epics) allow; where
committing is yours, it says so and you commit the spec yourself. Or take the refusal's own last
option and start the task with `--worktree`: the spec's changes stay in your checkout, untouched.

## `jig verify` refuses a change that no check covers, and blames your tools

{/* closed by jig task: verify-knows-a-change-maps-to-no-check — remove this entry in the PR that merges the fix */}

With `verify.full_run: ci`, a local `jig verify` runs only the checks your change can affect. When
it affects none of them — a change only to documentation, say — every check is skipped, and the
run exits 3 with:

```text
verify: nothing was checked, so this is not a pass — install the project's tools so its profile can run
```

Your tools are installed; `jig verify --list` shows it. Nothing was checked because nothing needed
checking, and the rule that refuses a run with nothing checked cannot tell that apart from missing
tools. So a change that touches only documentation cannot come out green locally, and the advice
sends you to install what you already have.

**What to do instead.** Read the skip reasons above that line. When the checks your tools run say
`scope:` — for instance `shellcheck: skip (scope: no changed shell scripts)` — the run was narrowed to nothing, not
starved of tools, and there is nothing to install. The full set runs in CI, which is what
`verify.full_run: ci` means.

## An interrupted command leaves temporary files behind

{/* closed by jig task: temp-files-die-with-the-command — remove this entry in the PR that merges the fix */}

When Jig rewrites one of its own files, it writes the new version *beside* the old one and then
renames it into place, so that a command stopped halfway can never leave you with half a file. What
it can leave you with is the spare copy. Press `Ctrl-C`, close the terminal, or let the machine
sleep at the wrong moment, and the spare stays where it was written. Nothing removes it afterwards.

They are easy to recognise: the name of a real file, then `.tmp`, then a number. A few are named
`.new`, `.join` or `.restore` instead, and one of those is a folder rather than a file.

```text
.ai/manifest.tmp.51827
AGENTS.md.tmp.51827
.ai/knowledge/adr/0042-how-we-deploy.md.tmp.51827
```

Most of them land in folders your project ignores and you will never meet them. The ones you do
meet sit next to files you care about, and your project reports them as new files it has not seen
before. That costs you twice: one can be committed by accident along with real work, and Jig counts
it as part of what you changed — so checks that would normally run only what your change can affect
may run everything instead, and take much longer for no reason.

**What to do instead.** Delete them. Nothing ever reads them back; the number in the name belonged
to the command that died. Look before you delete:

```bash
find . -path ./.git -prune -o \( -name '*.tmp.[0-9]*' -o -name '*.new.[0-9]*' \
  -o -name '*.join.[0-9]*' -o -name '*.restore.[0-9]*' \) -print
```

Check that the list holds nothing but names like these, then delete them — one of them may be a
folder, so remove it as one. Or simply hand the whole thing over:

```text Send to your agent
Find Jig's leftover temporary files, show me the list, and delete them.
```

<Warning>
  Do this when no Jig command is running. A file that looks like a leftover may be the copy a live
  command is about to rename into place.
</Warning>
