This page lists faults in Jig that you can run into without reading its source code. Each entry
says what you will see, what it can cost you, and what to do instead.

<Note>
  **What this page describes.** Jig as it stands today — the code the next release is cut from.
  It is not a report about one installed version, so your copy may behave differently.
  The [changelog](/changelog) is where each release records what changed.
</Note>

**This is not the page for "something went wrong".** If a command refused, a setting did not take,
or your agent ignored Jig, start with [Troubleshooting](/troubleshooting) — those are problems with
an answer today. An entry below stays here until the fault is actually fixed, and it is removed in
the same change that fixes it.

The page is not a list of everything Jig could do better, and it is not a copy of Jig's to-do list.
Work already under way is left out. For the order these are being fixed in, and what comes after
them, see [What's next](/roadmap).

{/* Closed by task staging-drift-report-findings: removed once a squash promotion is told from drift. */}
### A task promoted by a squash merge reads as staging work nobody owns

**What you see.** After a task's promotion is merged into the base branch with "squash and merge"
and its branch is deleted, `jig status` counts its commits in `staging: … commit(s) on staging that
no live task branch holds`. The squashed commit in the base branch is a new commit, so the task's
own commits on the staging branch are not in the base branch.

**What it costs.** The count stays up and stops saying anything useful; real drift hides behind it.

**What to do instead.** Merge promotions with a merge commit, not a squash: then the task's own
commits reach the base branch and leave the count. A squash merge into the staging branch has the
mirror fault, already known: the task reads as not on staging.

{/* Closed by task prepare-for-prod (F4): removed once a run against a real GitLab project confirms the path. */}
### "Prepare for prod" has not been tried against a real GitLab project

**What you see.** Nothing different, as far as is known. On GitLab, `jig task promote` looks up the
promotion and the staging merge request with `glab mr list --source-branch … --target-branch …`
(and `--all` for the staging one). Only GitHub has been checked against real projects; on GitLab the
answers are read the same way but have only been tried against a stand-in. Whether GitLab marks a
staging merge request merged once its branch is in the staging branch is not checked either.

**What it costs.** If `glab` answers differently, the command may not find a promotion that is
already open and try to open a second one, which GitLab refuses, or the pull request may get the
latest commit's subject as its title instead of the staging merge request's.

**What to do instead.** Check the merge request list on GitLab after the first promotion, and give
the title yourself with `--title` if it is not the one you want.
