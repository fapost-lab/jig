Jig is a framework for building software with an AI coding agent — Claude Code or Codex. You
describe what you want in plain words; the agent decides how careful the work has to be, keeps
the project's knowledge up to date, and stops to ask you where a human decision matters.

Jig lives inside your project. It adds a folder of project knowledge, a set of skills your agent
uses, and a small command-line tool the agent runs for the mechanical parts. Nothing is hosted,
there is no telemetry, and no script ever calls an AI model: the agent makes the engineering
decisions, the scripts only keep records straight.

## How working with Jig looks

You do not need to learn commands or skill names. You talk to your agent:

> **You:** Add CSV export to the reports page.
>
> **Agent:** This touches the report pipeline and the download endpoint, so I classify it as
> structural (T2): analyze, plan, implement, review, verify. I have created the task
> `csv-export` on its own branch. Here is what I found in the code and the plan …

Behind that answer, the agent picked the `jig-task` skill, looked at the risk of the change,
chose a route, created a task workspace and loaded only the project knowledge relevant to
reports. The agent usually picks the right skill from what you say; when it does not, name it —
`/jig-task` in Claude Code, `$jig-task` in Codex. A one-line typo fix gets a three-step route; a change to authentication gets design, your
approval and an independent review.

## Then hand more of it over

None of that asks you to trust the agent with your repository. When you decide to, you hand it
over in steps. The first and the last are settings in **your** copy of the project, never a
decision made for your colleagues; the middle one you grant a task at a time, by asking for it.

1. **Let it ship.** One line, `agent.git`, says how far a finished task travels: left in your
   working tree (the default), committed, pushed, or an open pull request you review.
   [Letting the agent ship](/agent-ships).
2. **Let it run the whole task.** On autopilot the agent goes from stage to stage without
   waiting for you, has a *second* agent review the code, gives itself at most two attempts to
   fix what the review or the checks found, and comes back with the change handed over — or
   with the one question it could not answer itself. [Autopilot](/autopilot).
3. **Let it run without questions.** If those questions are not yours to answer, it takes the
   careful option instead and writes down in the pull request every choice it made in your
   place. Together with the last `agent.git` level, `merge`, that is a change deployed without
   you — but only once your own CI has proved it.
   [Autopilot without stops](/autopilot#without-stops).

You can stop at any step. The two settings are as easy to take back as to grant — `jig config
unset` removes one and the default applies again — and autopilot is never on by default: it covers
the one task you asked for it on. Wherever you stop, `jig status` is where you look
([Seeing where things stand](/working-with-tasks#seeing-where-things-stand)).
