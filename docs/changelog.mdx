Jig is pre-1.0, so a minor version may change commands, the `.ai/` layout or the installer.
Update the tool with `jig self-update`, then run `jig upgrade` in each project and commit the diff
([Install](/install#keep-jig-up-to-date)). Releases are tagged on
[GitHub](https://github.com/fapost-lab/jig/tags).

## 0.22.0 — 2026-10-05

At a terminal, `jig doctor`, `jig upgrade`, `jig status`, the installer and `jig-setup` now say what
needs you first and group the rest, and an upgrade no longer refuses because of a session that only
looked around.

Everything below about a terminal is only the terminal. In a pipe, in CI and in an agent's shell the
output of `doctor`, `upgrade`, `status` and the installer is what it was: tests compare the whole
report of `doctor`, `upgrade` and `status` with the old text, and `install.sh`'s main runs (a
successful run with the PATH advice, the other-checkout note, an error). `install.ps1`'s plain form
is held by line-level assertions in every scenario, not by a whole-output comparison. `jig-setup` is
the exception: it is a skill, and it speaks in blocks wherever it runs.

- **`jig doctor` at a terminal lists what needs you first.** Failures, then warnings each with its
  fix, then every passing check in one line (`ok    13 passed: git, ...`), then the tally. The exit
  code does not depend on the form. The terminal form waits for the release check (up to 5 seconds)
  before it prints; the piped form still streams each check as it runs.
- **`jig upgrade` at a terminal says what changed, not every file.** Replacements are grouped into one
  line per verb (`ok    replace 50 file(s): .ai/scripts (14), .claude/skills (17), ...`); installs,
  deletions and links stay one line each, and every file the upgrade kept is a `warn` line. Measured
  once, on a project installed from v0.18.0 and upgraded on a real pseudo-terminal, 58 files placed: 66
  lines before, 17 after. A run that dies midway names none of the files it had replaced at a
  terminal; the repeat that finishes it reports them as already placed.
- **`jig status` at a terminal puts what needs you first.** Failures and warnings come first, each with
  its `hint:`, `fix:` or `see:` line, then the rest grouped; with nothing to do the last line reads
  `nothing needs you`. Measured once in this repository on a real pseudo-terminal: 31 lines before, 12
  after. The status page, `jig doctor` and `status-counts` read the plain report and are unchanged.
- **The installer speaks the same blocks.** `install.sh` and `install.ps1` print a level word
  (`ok`, `warn`, `fail`, and `ask` for a question) padded to six columns, with the PATH advice and the
  other notices before the closing `ok    jig installed: ...`; an error is a `fail` block. The
  PowerShell installer colours through the console (`ok` green, `warn` yellow, `fail` red, `ask` cyan),
  never through escape codes, and runs `jig doctor` in its grouped form without colour. `jig-setup`
  asks and reports in the same form.
- **Output switches.** `JIG_TERMINAL=1` forces the terminal form and `JIG_TERMINAL=0` the plain one;
  `NO_COLOR` (any non-empty value) and `TERM=dumb` remove colour and keep the grouping. A reader that
  needs the old text under a terminal sets `JIG_TERMINAL=0`.
- **An upgrade refuses only where a started task holds this checkout's branch.** `jig upgrade` used to
  refuse because another session had run `jig status` hours earlier, or `jig task show` on a task not
  checked out here, and the only way out was deleting a file the message did not name. It now refuses
  only when you are on the branch of a started, unfinished task (the upgrade would take the checkout
  off it); the message names the task, its branch and the way on: `jig task start <id> --worktree`,
  then the upgrade again, or, inside the task's own worktree, the upgrade in the main checkout. A
  session that only looked around no longer stops it. `jig task start` and `jig upgrade` now answer
  "who occupies this checkout" with one rule. `jig verify` running here still stops an upgrade.
- **The upgrade's "run it in the main checkout" advice is right for a worktree of a bare repository.**
  The upgrade asked Git directly whether it was in a linked worktree and, for a worktree of a bare
  repository, pointed at a main checkout that does not exist; it now asks the way the rest of Jig does.

What was proven where: by tests on throwaway repositories and in CI. The terminal forms of `status` and
`upgrade` were measured on macOS and Linux pseudo-terminals; on Windows CI only proves that
`JIG_TERMINAL=1 jig doctor` runs in Git Bash and that the shards pass (the byte-for-byte doctor test
skips there). Not proven by anything kept: that the colours render in Windows Terminal or the Windows
PowerShell 5.1 console, that `ask` and the typed answer share one line there, and that the
home-folder refusal reads as an instruction. The Windows release checklist was not walked on a real
machine for this release.

## 0.21.0 — 2026-10-05

A task can no longer be finished past a stage its class asks for, an epic finishes without a push to
the epic branch, and your agent can hand writing and reviewing the code to a helper on a model you
choose.

- **A task whose route skipped a recorded stage is refused.** `jig task set <id> status ready`,
  `jig task set <id> knowledge_consolidated true` and `jig task ship` read the class's full route and
  refuse when a stage that leaves a record left none, naming what is missing and the command that
  writes it: the approved design for T3 and T4 (the approval must still match `design.md`), `spec.md`
  and `alternatives.md` for T4, a review receipt for the review of T2 and up and for the architecture
  review of T3, and `status ready`, verification's own sign-off, before consolidation and shipping. A
  lighter route (`route.depth: lean`) trims none of this, and a task filed with this version and given no class is refused. A task
  filed before this version is not refused: it gets the same list as a warning and finishes under the
  rules it started with. A review receipt now remembers every stage it was written for, so a re-review
  under another stage does not erase the first. Proven by tests on throwaway repositories that run both
  directions; no run on a real project is kept.
- **Lowering a class needs a reason, and an unattended run cannot lower a risky one.**
  `jig task set <id> class T1 --reason <text>` records the reason and the class it came from, and
  `jig task route`, `jig status` (`lowered=T3`), the status page and the autopilot report show it. Where
  nobody answers (an unattended clone or run), a task cannot be lowered below T3 out of T3 or T4. Raising
  a class is unchanged.
- **An autopilot run cannot resume itself.** `jig task autopilot <id> resume` now needs
  `--answer <the human's answer>`, which is journaled and printed in the report under "Resumed on an
  answer"; in an unattended run `resume` is refused, and `end` there requires `knowledge_consolidated
  true`, so a run cannot reset its repair limit by ending and starting again. `jig task gate <id>
  approved` without `--by agent` is refused wherever nobody answers: in an unattended clone, whether
  the run is not started, on or stopped. In an attended clone nothing changes.
- **A planted link cannot send a task's files elsewhere.** A link planted on `.ai/workspace`,
  `.ai/workspace/tasks` or a task's own entry used to slip past the check of `jig task artifact write`
  and `append` (a planted `tasks` link wrote `plan.md` outside the repository with exit 0). Every
  command that writes into a task workspace, `jig task new`, `jig spec link` and `remove` and
  housekeeping included, now follows the link to where it leads, symbolic link or Windows junction alike,
  and refuses unless that is this checkout or a worktree Git lists for this repository. The links
  `jig task start --worktree` makes and a coordinator's own `.ai/workspace` link keep working. The
  junction case was exercised by tests that plant links the way Windows CI does, not by hand on a real
  Windows machine.
- **An epic finishes without a push to the epic branch.** `jig spec epic --finish` and `--reopen` run on
  the epic or on a branch cut from it, and the final `jig spec ship` cuts `finish/<id>` from the epic,
  commits the spec's removal and the version bump there, and opens the pull request into the default
  branch from it. The epic is never pushed after it is cut, so a repository that protects `epic/*` like
  the main branch needs no bypass; the `epic-pr` check accepts a `finish/<id>` head. See
  [Agent ships](/agent-ships).
- **New personal setting `release.merge`.** `agent` (the default) keeps today's behaviour: an unattended
  run at `agent.git: merge` merges an epic's final pull request once CI passed. `human` opens it and
  leaves the merge to you. Local only, set with `jig config set release.merge human --local`; task pull
  requests are not affected. See [Configuration](/configuration).
- **Hand writing and reviewing the code to a helper on a model you choose.** Two new personal settings,
  `claude.implement_model` and `claude.review_model` (set by hand or through a new `jig-setup`
  question), name the model a helper agent in Claude Code uses for the implementation and for every
  review of a route; `jig task route <id>` prints a `delegate:` line for each stage that will be handed
  over. Jig carries the name as written and never checks it. With nothing set, the default, nothing is
  handed over and every route runs as before; in Codex the settings are ignored. The helper's findings
  and receipts count like anyone's: the checks still have to pass. Proven by tests of the settings and
  of the `delegate:` lines; no run of a helper on another model is kept as a test. See
  [Autopilot](/autopilot#helpers-on-another-model).
- **`jig-verify` no longer leaves a log in your working tree.** The skill used to tell the agent to
  redirect `jig verify` into `verify.log` in the project; the report now goes to the terminal.

## 0.20.0 — 2026-10-03

A started task can be moved into a worktree of its own, a worktree can share a folder of packages
with its checkout, a person can choose a lighter route, and an agent can plan a release.

- **A task that has already started can move into its own worktree.** `jig task start <id> --worktree`
  on a started task (with `git.branch_per_task` on) used to refuse with "already started"; it now
  frees the branch in this checkout,
  adds the worktree on it, links the workspace and carries the declared state. Commits made so far stay
  on the branch. It moves nothing that is not safe to move: when this checkout holds its branch and has uncommitted changes to tracked files it
  refuses and names `jig task pause <id> --stash`, and the checkout goes back to the task's base branch;
  every refusal comes before anything changes, and a failure afterwards puts the checkout back on the
  branch. The branch is never deleted. Moving back out of a worktree stays with Git. The "HEAD moved"
  notice now names this command. This was tried in tests on throwaway repositories.
- **New setting `worktree.share`.** For a project that keeps separate repositories under edit beside its
  code (a `packages/` folder, Composer path repositories): `worktree.share: [packages]` gives each task
  worktree a real `packages/` folder in which every entry is a link (a junction where symbolic links
  cannot be made) to the package in your main checkout. There is one copy of each package, and removing
  the worktree, by Jig's cleanup or by `git worktree remove`, removes the links and never the packages. A
  test makes a commit and leaves an uncommitted file through the worktree, removes it with a bare
  `git worktree remove`, and finds both in the owner's checkout; the same steps with `carry`, tried by
  hand on 2026-09-24 and not kept as a test, lost the commit. The folder must be in `.gitignore`; a package added later is linked in by `jig task bootstrap
  <id>`; a path declared as both `carry` and `share` is shared. Jig refuses a shared folder that is itself
  a Git repository. The known issue about removing a carried worktree by hand is gone, and
  [Working with tasks](/working-with-tasks#sharing-a-folder-of-packages-you-edit) says how to set it up.
  The junction path is exercised by the Windows CI job, not by hand on a real Windows machine.
- **New personal setting `route.depth`, and `jig task route`.** `route.depth: lean` (set with
  `jig config set route.depth lean --local`; the default is `full`) lets you run less of a class's route:
  a T1 analysis is a few lines in `task.md`, a T2 plan is part of the analysis, and T2 to T4 run one review
  round, with P2 and P3 findings left open and listed in the pull request. Tests on changed files, CI
  before a merge, consolidation, the T3/T4 gate and architecture review, a re-review of a fixed P0/P1 and
  the task's class are never trimmed. A value in `.ai/config.yaml` is ignored and reported, as for
  `agent.git`. For one task: `jig task new <id> --lean`, or `jig task set <id> route_depth full|lean`; the
  task's own value wins. `jig task route <id>` prints the class, the depth and where it came from, the
  route and what lean trims. `jig status` marks a lean task `depth=lean`, the status page badges it, and
  `jig task autopilot start` and `report` print the depth. See [Concepts](/concepts).
- **`jig-release`: an agent can plan a release.** A new skill (placed by `jig upgrade`) looks at the filed
  tasks and open specs, proposes what goes in, in what order and at what version level, and, once you
  agree, builds the release as a spec with an epic. `jig spec link <spec-id> <task-id>` links a task filed
  earlier (it refuses a started one, a closed one, or one linked elsewhere), and `jig task list --goals`
  prints the first paragraph of each task's goal under its line. See [Skills](/skills). The skill was
  proven by its tests and by being used for this release; it has no run of its own beyond that.
- **A review stays valid when the base moves.** The review receipt used to pin the whole working tree, so
  merging the base into a task branch made it stale even when the task's own change had not moved. It now
  compares four things by content: the task's own change against its merge base, the knowledge `jig
  context` resolves for that change (without the knowledge the task wrote itself), the approved design and
  the findings. The stale message says which part moved. A receipt written before this version is
  compared by the working tree until the next review rewrites it. Two consequences to know. An unrelated
  merge that edits a global knowledge document (the glossary, the architecture, the rules), or a document
  that applies to the files the task changed, still makes a receipt stale, because `jig context` returns
  those. And every receipt check now resolves that knowledge, which `jig status`, the `ready` status
  and `jig task ship` all run, and the cost grows with the [known issue](/known-issues) that `jig context`
  is slow on a large project. `jig status` therefore no longer resolves it: it compares the change, the
  design and the findings, and for a receipt that still matches says `not checked` rather than `current`;
  `jig task receipt --check`, the `ready` status and `jig task ship` still check everything. Measured on
  five tasks that each had a receipt and a worktree, `jig status` took 51 s with the check on every task
  and 9 to 11 s without it. The roadmap entry for this is gone.
- **Skills write a task's own documents through `jig task artifact`.** The command takes three more kinds,
  `knowledge-map`, `commit-message` and `pr-body` (the files are `commit-message.md` and `pr-body.md`), so
  `jig-consolidate`, `jig-map` and a phase run no longer write them with a shell redirect, which
  `jig-task` forbids. `jig-review` and `jig-architecture-review` keep the list of changed paths in a shell
  variable instead of a workspace file.

## 0.19.0 — 2026-10-02

`jig verify` now knows the common local PHP environments, runs every built-in profile where your
project runs, and `jig doctor` says when this machine's runtime is not the one your project asks for.

- **More environments are recognised, so fewer projects are refused.** DDEV (`.ddev/config.yaml`,
  through `ddev exec --raw`), Lando (`.lando.yml`) and a devcontainer (`.devcontainer/devcontainer.json`,
  through the `devcontainer` CLI when it is installed, otherwise the labelled container) now have
  detectors; Lando and a devcontainer without its CLI are reached with `docker exec`. A stopped one is
  refused with its start command (`ddev start`, `lando start`, `devcontainer up`); a shell already
  inside one of them runs on the spot. Jig still refuses a `.devcontainer/` or `.ddev/` folder without
  its manifest. **Devilbox** is found by its PHP container (compose service `php`, data folder mounted
  at `/shared/httpd`) wherever your data folder lives, and its checks run there as Devilbox's own user.
  **Laravel Herd** is found when the project is one of Herd's sites; its checks run on this machine
  with Herd's `bin` folder first on `PATH`. Devilbox's detection was tried against a real running stack (the container was found and `php -v`
  ran through the prefix); a full `jig verify` there, and its refusals, were exercised only with
  stand-ins. DDEV,
  Lando, the devcontainer CLI and Herd were exercised only with stand-ins for their commands and
  fixture files, never a real install; if one is not recognised or answers wrongly, `run.exec` and
  `run.path` override it ([Configuration](/configuration#where-checks-run)).
- **New personal setting `run.path`.** A folder put first on `PATH` for the checks when they run on this
  machine, for a PHP that is not first there; `auto` (the default) uses what Jig detected (Herd's).
  Blanks are allowed in it; it must be an absolute folder that exists, and a missing one is refused.
- **Every built-in profile runs where your project runs.** The `shell`, `python`, `go`, `rust`, `ruby`,
  `jvm`, `dotnet`, `dart` and `swift` profiles joined `php`, `laravel`, `node` and `generic`: inside an
  environment their checks go through its prefix instead of being skipped. Under an environment, Python
  does not use the `$VIRTUAL_ENV` or poetry of this machine; its tools come from a `.venv/` or `venv/`
  that runs there, otherwise from the environment's own `PATH`. This was tested with a stand-in for
  `docker` whose tools exist only inside the "container", not in real containers.
- **`jig doctor` and `jig verify --explain` warn when this machine's runtime is not the one your project
  asks for.** When the checks run on this machine, Jig compares the PHP, Node and Python found here with
  `require.php` in `composer.json`, `engines.node` in `package.json` and `.python-version`. Common forms
  (`^`, `~`, comparisons, wildcards, "and", "or") are judged; any other form is reported as "could not
  compare", never as fine, and so is a runtime that is not installed on this machine. `jig doctor` also
  lists the runtimes that match; `jig verify --explain` prints only the warnings. Nothing is said when
  your project asks for nothing, or when the checks run in an environment. These are warnings: they do
  not stop `jig verify`.
- **`jig task start` refuses less often.** Only a task that has been started, is not finished, and holds
  the branch checked out in this checkout now counts as working in it. A session that only filed a task
  with `jig task new` or ran `jig status` no longer blocks the next start. The refusal and
  `jig upgrade`'s matching stop no longer advise deleting the other session's record: it lapses by itself
  after `checkout.busy_ttl`.
- **Paths with a backslash no longer confuse container detection.** The container reader now passes
  project paths to `awk` in a way that keeps backslashes as they are.

## 0.18.0 — 2026-10-02

`jig verify` learns to run a project's checks where the project runs, and Jig stops leaving its
scratch files behind.

- **`jig verify` runs the checks where your project runs, and refuses rather than guess.** Before any
  check, it decides once whether the commands go to this machine or through a prefix that reaches
  your container, and says so — `verify: checks run in <where>` — with `--explain`, and whenever the
  checks go through a prefix. **Laravel Sail** and a **docker
  compose** service that mounts the project are recognised on their own; the new personal setting
  `run.exec` (`auto`, `host`, or the command that reaches the container, written in plain words with
  no quotes, `$` or backslashes) overrides what Jig found.
  When there are signs of a container no detector recognises — two compose services mounting the
  project, `DB_HOST` naming a compose service, a `.devcontainer/`, `.ddev/` or `.lando.yml` — Jig
  exits 3 and names what it saw instead of running the checks on the host; a stopped container, or
  one that mounts another checkout than the task's worktree, is refused the same way. The `php`,
  `laravel`, `node` and `generic` profiles run through the environment; when checks run in one, a
  profile not yet adapted is skipped with the reason, never run on the host. With `CI` set and
  `run.exec` left at `auto`, nothing is detected and nothing is refused. The `jig-setup` skill now asks where your tests run, as its eighth question
  ([Configuration](/configuration#where-checks-run), [Troubleshooting](/troubleshooting)).
- **`jig task start` refuses a checkout another session is working in.** It reads the record every
  Jig command already writes in the checkout and, when other work is live there, stops and names the
  owner, how long ago it ran, and the ways out: start in its own worktree (`--worktree`), wait, or
  delete the record if that session is over. There is no override. It does not apply to
  `--worktree`, to a project on one branch, or to records of tasks that are consolidated or
  abandoned, or whose branch is no longer the one checked out.
- **An interrupted Jig command removes its own temporary files.** `Ctrl-C` (SIGINT) and SIGTERM now end
  a command with exit 130 and 143 and run its cleanup, and the temporary files and folders Jig makes
  are removed when the command exits or is stopped by either signal — the `*.tmp.<pid>` files that
  used to pile up beside your project's files. A command killed with SIGKILL cannot clean up, and a
  closed terminal is not caught either. The test runner no longer leaves its `jig-*` folders in your
  temporary directory (more than 4,600 had piled up at once).
- **A shared shell library change narrows what `jig verify` runs.** With the `shell` profile, a
  change to a script that has no test file of its own (`scripts/lib/common.sh`, say) now runs the
  tests of the scripts that call the functions it edited, instead of the whole suite. When it cannot
  name them — a changed global, a `source`, a new or removed function or file, a function nobody
  calls, a caller with no test — it still means the whole suite. With `verify.full_run: ci`, that
  whole-suite part is left to CI when filters ran beside it, and the line says so:
  `scope: N filters, full set left to CI`.
- **`load: domain` knowledge reaches the files it names.** A document with `load: domain` was
  required only when its domain was entered; its `paths` were ignored. `jig context` now requires it
  for a matching domain or a matching file, so an agent editing a file a domain pack names gets the
  pack without passing `--domains`. Cached answers made under the old rule are not served.
- **The status page redraws after knowledge commands.** `jig knowledge new`, `paths`, `reviewed`,
  `accept` and `reject` now refresh the `jig status --html` page they changed, so its proposal and
  changed-source counts are no longer stale until the next task command.

## 0.17.1 — 2026-09-30

No change to how Jig behaves. One test of 0.17.0's `jig doctor` `latest release` line was wrong on
Windows: it rejected any output containing "available", and Windows prints
`directory links: junction (symlinks unavailable)`. The test now checks only the `latest release`
line, and the release's test suite passes on Windows again.

## 0.17.0 — 2026-09-30

`jig upgrade` becomes a change of its own, and the installer and Windows checkout gain the fixes
0.16.1 was too small to carry.

- **`jig upgrade` now runs as its own change, on its own branch.** It checks first that it may
  start — no uncommitted changes, no `core.autocrlf` without Jig's files pinned to LF, no other
  session or `jig verify` busy in this checkout — then works on `jig/upgrade-<version>`, cut from
  your base branch, and commits once the result checks out. It ships as far as your agent's git
  rights allow, the same as `jig task ship` ([Upgrading](/upgrading#an-upgrade-is-a-change-of-its-own)).
  The commit and its pull request now also carry a checklist of the manual steps left between your
  version and the new one, instead of a fixed pointer at this page.
- **`jig doctor` tells you when a newer Jig has shipped.** Its `latest release` line asks the
  tool's own origin for the newest published tag, instead of only comparing your project against
  the copy on your machine — so the two can agree and still both be behind. It tells apart a real
  "you're behind" from "could not check" (no network, no origin, no answer in time), and never
  reports either as "up to date" by mistake ([Upgrading](/upgrading)).
- **`jig status` shows a newer Jig release too, without running `jig doctor` for it.**
  Housekeeping now checks the same thing once a day in the background and keeps the answer; `jig
  status` (plain text and the `--html`/`--open` page) reads it offline and, the moment a newer
  release is out, prints `jig v<X> is out — jig self-update, then jig upgrade`. No network call of
  its own, and nothing shown when there is nothing new or the check failed.
- **The Windows installer no longer refuses a drive or share root that is already your
  repository.** A `subst` drive, a volume kept for one project, or a `\\server\share` that is
  itself the top of an existing repository now installs the project too, not only Jig
  ([Known issues](/known-issues)).
- **A Jig project cloned on Windows keeps taking upgrades.** Line endings are now pinned for all
  of `.ai/manifest`, `.ai/scripts/**`, `.ai/profiles/**`, `.ai/templates/**` and both adapters'
  skill directories, not only the scripts — a clone or task worktree made with Git's default
  `core.autocrlf=true` no longer reads its own manifest as empty
  ([Upgrading](/upgrading#from-0161-to-0170)).
- **`jig housekeeping` no longer hangs waiting for a credential prompt nobody can answer.** Every
  network `git` call it and `jig self-update` make now refuses to prompt, so a remote that would
  otherwise ask for credentials fails fast instead of piling up one stuck process per session.
- **A task can no longer be closed while its pull request is still open.** `jig task set <id>
  status consolidated` now checks with the forge first and refuses unless the pull request has
  actually merged, so a task does not disappear from `jig status` while it still needs a merge.
- **`jig verify` tells a change no check covers from missing tools.** A documentation-only change
  used to refuse with "install the project's tools", even though the tools were already there. It
  now recognises a skip explained by scope and passes instead of blaming your setup
  ([Known issues](/known-issues)).
- **The front-end cut now reaches Python, Ruby, Dart and Node projects.** A stylesheet, image or
  front-end source file that a project's own test suite cannot observe no longer forces the full
  set to run, the way it already worked for PHP and Laravel — each stack keeps its own build and
  fixture exceptions, and the reason now names the file that forced a full run.
- **`jig context` and `jig knowledge check` are markedly cheaper on a real repository.** One shared
  tree walk replaces a filesystem `find` per path pattern of every document (291 finds down to one
  walk, on an 83-document project measured at 30-39s before the fix); a task's repeated
  `resolve`/`guard` calls with the same selectors now reuse their answer instead of recomputing it,
  measured at roughly 6x faster (about 8s down to about 1.3s on an 89-document project)
  ([Known issues](/known-issues)).
- **A second session on a spec no longer leaves it sitting dirty on your default branch.**
  `jig spec new` and the new `jig spec resume <id>` switch to the spec's own branch first, the same
  branch `jig spec ship` already used; `jig task start`'s dirty-tree refusal now names
  `jig spec ship` when every uncommitted change belongs to one spec.
- **The status page's own redraw no longer swallows a neighbouring session's "HEAD moved" notice.**
  Refreshing `jig status` runs `jig status` again as a subprocess; that subprocess is now marked
  internal so it cannot consume a checkout notice meant for another session.
- **A reason or note you type is stored exactly as typed.** `jig task pause --reason` and similar
  free-text values could have a backslash sequence reinterpreted on the way into the task's state
  file — a Windows path like `C:\temp` no longer risks being mangled or splitting into a second,
  bogus state line.

## 0.16.1 — 2026-09-28

Fixes to what 0.16.0 shipped: the Windows installer, `jig upgrade`, and how much a PHP project's
checks run.

- **The Windows installer no longer turns your home folder into a Git repository.** Taking its
  defaults from a fresh PowerShell used to make your whole profile a repository and commit
  everything in it. It now refuses your home folder, any folder above it, the root of a drive and
  a folder inside another Git repository, and `-Yes` does not change that. Asked interactively,
  it says why and asks for another folder; Jig itself is installed either way
  ([Install](/install)).
- **It also refuses a folder it should not, which 0.16.0 accepted:** the root of a drive or a
  network share that is itself the top of an existing repository — a `subst` drive, a volume kept
  for one project, `\\server\share`. Jig is installed, only the project step stops; run
  `jig init` in that folder yourself ([Known issues](/known-issues)).
- **An interrupted `jig upgrade` is finished by running it again.** A file that already holds the
  new version is recognised as placed, reported `already-placed`, and no longer mistaken for your
  edit. A project an earlier interruption left in that state heals on the first run of this
  version, with nothing to reconcile by hand.
- **`jig upgrade` says what it left undone.** At the end of a run it asks the install it has just
  made whether anything is still missing, names it, and tells you to run `jig upgrade` again —
  instead of leaving it for `jig doctor` to find a day later.
- **Repositories with SHA-256 object names, or with clean filters, upgrade properly.** Every
  framework file used to read as modified in the first kind, and the filtered paths in the
  second, so those files stopped being updated. Upgrade with `jig self-update` and `jig upgrade`;
  if your agent runs the project's own `.ai/scripts/jig upgrade`, these two kinds of project need
  one more step ([Upgrading](/upgrading#from-0160-to-0161)).
- **A front-end change in a PHP or Laravel project no longer runs the PHP test suite.** When a
  scoped `jig verify` does run the whole suite, it now names the file that caused it —
  `scope: package.json changes the asset build, which browser tests load, ran full set` instead of
  `scope: not narrowable, ran full set`.

## 0.16.0 — 2026-09-25

Green now means green.

<Warning>
  **Do this after upgrading: install the tools your project's checks need.** `jig verify` used to
  answer `ok` when a profile for your stack was active and every one of its checks had been
  skipped for a missing tool. It now refuses — **exit 3**, *nothing was checked, so this is not a
  pass* — and `jig task ship` will not ship on it. `jig verify --list` shows which profiles are
  installed; install what they need (`npm install`, `composer install`, a virtual environment,
  `shellcheck` …). If you wrote a profile of your own that deliberately checks nothing, add
  `verifies: nothing` to its `profile.yaml`: absence means the profile asserts something, so it
  refuses rather than quietly becoming unverifiable
  ([Troubleshooting](/troubleshooting#verification-and-upgrades)).

  **And if `jig upgrade` reports `keep-unmarked AGENTS.md`: run the `jig-init` skill.** This
  release keeps the Jig section of your `AGENTS.md` current through an upgrade — but only for a
  project whose manifest carries Jig's claim to that region, and `jig init` is the only thing that
  writes that claim, on markers you agreed to. Adding the markers by hand does not do it: without
  the claim every outcome stays a `keep-`. If your section has also drifted from Jig's own text,
  markers alone are still not enough — no claim is recorded and `upgrade` goes on reporting
  `keep-modified`. Reconcile the text with `.ai/templates/AGENTS.md` first, then mark it. That
  nothing does this for you is deliberate: the first time Jig claims a region of a file your
  project already had is a moment that belongs to you.

  All three of this release's manual steps — these two and `verifies: nothing` — are set out with
  the commands that prove they took on [Upgrading](/upgrading).
</Warning>

- **A pass now means something was checked.** Two states used to be one. A project whose stack a
  profile covers, but whose tools are missing, is refused (above). A project **no** profile covers
  is not blocked — there is nothing to install and nothing to wait for — but it is not called `ok`
  either: `jig verify` says *nothing here checks this project* and exits 0, and `jig task ship`
  says it again as the change leaves your machine.
- **`jig task ship` refuses instead of shipping nothing.** An empty index with unstaged changes
  used to print a note and carry on — pushing the branch and opening a pull request with the
  change left behind, where nothing makes CI red. It is now an outcome, not information. An empty
  index with a clean working tree still proceeds: that change was committed by an earlier run.
- **Two verifications no longer fight for the machine.** `jig verify` waits for one already
  running in the same clone and says how long it waited (`verify.busy_ttl: 0` turns the wait off).
  A run that was *killed* — out of memory, an overloaded machine — reports **incomplete** and
  exits 3 instead of counting as a pass.
- **`jig verify --explain` says what a run will expand to, before it runs.** One line per check —
  `full`, `filtered`, `skip` or `conditional` — so you can see that a change to a widely-used file
  means the whole suite before you start it. It takes no busy record, runs no project tool and
  produces no verdict ([Manual control](/manual-control)).
- **A task worktree is a place you can actually work in.** `worktree.carry` copies the state Git
  does not track — `vendor/`, `node_modules/`, `.env` — into a new worktree, beyond what the
  active profiles already declare ([Configuration](/configuration#git-and-branches)). And removing
  a worktree now asks every Git repository inside it first: a clone holding work that exists
  nowhere else keeps the worktree rather than going with it.
- **A task filed from inside a worktree no longer disappears with it.** A worktree borrows its
  checkout's whole task directory rather than the single task it was made for, so a task an agent
  files while working in one is visible from the main checkout and survives the worktree being
  removed. Measured on Windows too, where the borrowed directory is a junction.
- **The status page stopped saying what it cannot know.** It keeps your place across its own
  auto-refresh, reports what it actually knows about a pull request instead of inferring it, drops
  a card the disk has already disproved, and shows the pull request of a task whose autopilot
  stopped.
- **Several sessions in one checkout see each other.** Every run records in the checkout's
  gitignored `.ai/runtime/` that work is happening here; `jig status` gains a `working here:` line
  for each live record, and the commands a session orients itself with warn it, on stderr, when
  HEAD moved underneath it.
- **`jig upgrade` keeps your instructions current.** For a project that has made the claim above,
  it refreshes the Jig section of your `AGENTS.md` instead of leaving it on the version it was
  written for, and no longer replaces a Windows project's CRLF line endings with LF when it does.
  `jig status` also reports the config keys your `.ai/config.yaml` no longer mentions —
  capabilities a new version brought that nobody offered you.
- **Jig acts on the repository you ran it in.** `GIT_DIR`, `GIT_WORK_TREE` and the other variables
  that choose what git acts on are cleared, so jig started from a git hook or an editor that
  exports them no longer writes its records into another repository.
- New pages: [Upgrading](/upgrading), what an upgrade does for you and what it leaves to you;
  [Known issues](/known-issues), faults in Jig itself and what to do instead; and
  [What's next](/roadmap), the order the open ones are being fixed in. `schemas/profile.md`
  documents the keys of `profile.yaml` for anyone writing their own.
