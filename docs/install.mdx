Set up Jig once on your computer, then connect it to each project you want to work on.
You can ask your AI agent to help with the project setup below.

## Before you start

You need three things:

- **An AI coding app** such as [Claude Code](https://claude.com/product/claude-code) or
  [Codex](https://openai.com/codex/), installed and signed in. It must be able to
  open a folder on your computer and edit its files. You use your own AI account.
- **A project folder.** An empty folder is fine for a new idea. For existing work, open the folder
  that contains the project's files.
- **Git**, the tool that saves the history of your files. If it is missing, follow
  [Git's installation guide](https://git-scm.com/book/en/v2/Getting-Started-Installing-Git).
  The Windows installer below can install it for you.

<Accordion title="What is a terminal, and where do I paste commands?">
  A terminal is an app where you give your computer written commands. On macOS, open **Terminal**
  using Spotlight. On Windows, open **PowerShell** from the Start menu. On Linux, open your
  **Terminal** app.

  Copy a command, paste it into the terminal, and press Enter. Wait for it to finish before
  pasting the next one. Messages labelled **Send to your agent** go into your AI chat instead.
</Accordion>

## 1. Install Jig on your machine

Choose your operating system. These commands download and run Jig's installer; expand the details
if you want to inspect the script or see what it changes first.

<Tabs>
  <Tab title="macOS and Linux">
    Paste this into Terminal:

    ```bash
    curl -fsSL https://raw.githubusercontent.com/fapost-lab/jig/main/install.sh | bash
    ```

    Open a **new terminal window** when it finishes.

    <Accordion title="What the installer changes and system requirements">
    The installer:

    - clones Jig into `~/.local/share/jig`, at the newest release;
    - links `~/.local/bin/jig` to it;
    - only when `~/.local/bin` is not on your `PATH` yet, adds one marked line to `~/.zshrc`,
      `~/.bashrc` or `~/.profile`.

    It needs no `sudo` and does not touch the folder you ran it from. Open a new terminal
    afterwards so the new `PATH` is picked up. Running the line again is safe: it moves a clean
    installation forward and refuses to overwrite anything it did not create.

    Jig needs Bash 3.2 or newer, Git and the standard Unix tools, all of which macOS and Linux have.
    WSL2 works as Linux; keep the project on the Linux filesystem, not under `/mnt/c`.
    </Accordion>
  </Tab>
  <Tab title="Windows">
    Paste this into PowerShell:

    ```powershell
    irm https://raw.githubusercontent.com/fapost-lab/jig/main/install.ps1 | iex
    ```

    Follow its questions. For a new project, you can let it create and set up your project folder.
    Open a **new terminal window** when it finishes.

    <Note>
      If Git is missing, the installer installs it. It may ask for your name and email for Git;
      these settings apply to other projects too. Use an empty folder for a new project:
      when the installer creates a repository, its first saved version includes everything there.
    </Note>

    <Accordion title="Installer details, options, and uninstalling">
    It says what it does as it goes:

    1. **Git for Windows**, only when it is missing — through winget (it tells you this accepts
       the winget source and package agreements for you), or the official installer when winget
       is not there.
    2. **Jig** into `%USERPROFILE%\.local\share\jig`, at the newest release, with its `scripts`
       folder added to your user `PATH`.
    3. **Your first project**, if you agree — at most four questions: which folder, whether to make
       it a Git repository, your name and e-mail for Git (only when Git has none; they are set
       globally, for every repository), and whether to set up Jig there. Before that last question
       it tells you what setup adds, including a Claude Code session hook that tidies up finished
       task workspaces in the background. A folder it turned into a repository gets one first
       commit of everything in it; an existing repository gets no commit.
    4. **`jig doctor`**, which checks everything above.

    Everything it prints also goes to `%LOCALAPPDATA%\jig\install.log`. Open a new terminal
    afterwards so `PATH` is picked up.

    To pass options, run the downloaded script as a block — for example `-NoSessionHook` to leave
    the session hook out, or `-Uninstall` to remove Jig again:

    ```powershell
    & ([scriptblock]::Create((irm https://raw.githubusercontent.com/fapost-lab/jig/main/install.ps1))) -NoSessionHook
    ```

    Other options: `-Project <folder>`, `-Yes` (no questions, defaults), `-GitName`, `-GitEmail`,
    `-NoInit` (no project step), `-Ref vX.Y.Z` or `-Ref main`. `-Uninstall` removes the `PATH` entry
    and the Jig folder only when it holds no local changes; Git for Windows stays.

    Claude Code runs Jig through Git Bash; Codex, which runs PowerShell, calls
    `.ai\scripts\jig.cmd`, which hands the command to Git Bash.
    </Accordion>
  </Tab>
</Tabs>

In the new terminal, check that Jig can run:

```bash
jig doctor
```

**What to expect:** a list of checks, with a suggested fix for each warning. Project checks appear once you are inside a Git repository.
If it says the project is not initialized, continue to step 2. If it says
`command not found`, see [installation help](/troubleshooting#installation).

<Accordion title="Read the script before running it, or install without it">
  To read the macOS/Linux installer first:

  ```bash
  curl -fsSLo /tmp/jig-install.sh https://raw.githubusercontent.com/fapost-lab/jig/main/install.sh
  less /tmp/jig-install.sh
  bash /tmp/jig-install.sh
  ```

  Its options: `--ref main` installs the development channel instead of a release, `--ref vX.Y.Z`
  a specific release; `--install-dir`, `--bin-dir` and `--no-path` change where things go and skip
  the startup-file line.

  Without the installer, clone Jig into a permanent folder and put its executable on `PATH`:

  ```bash
  git clone https://github.com/fapost-lab/jig.git "$HOME/.local/share/jig"
  ln -s "$HOME/.local/share/jig/scripts/jig" "$HOME/.local/bin/jig"
  ```

  A clone made this way follows `main`, the development channel.
</Accordion>

## 2. Set up a project

Open your project folder in your AI coding app. Then send:

```text Send to your agent
Help me set up Jig in this folder. Check whether it is already a Git
repository and whether Jig is initialized. Do only the missing setup.
If there is existing work, show me what needs saving first.
Make sure the agent instructions include Jig's workflow.
Show me what was added and help me make the initial setup commit.
```

A **repository** is a folder whose history Git tracks. A **commit** is a saved version of its
files. That first saved version is needed before Jig can start tasks on separate branches.

<Warning>
  **Already have agent instructions?** Jig preserves your existing `AGENTS.md` and `CLAUDE.md`.
  Ask the agent to connect Jig to them and review the section it proposes. Until those files
  include Jig's workflow, the agent may not use Jig automatically. Keep the
  `<!-- jig:begin -->` and `<!-- jig:end -->` lines around the section it adds: they are what lets
  later `jig upgrade` runs keep it current.
</Warning>

<Accordion title="For developers: set up an empty project by hand">
  After installing Jig, run these commands in a terminal. Use Git Bash on Windows for this example.
  Choose a new folder name rather than a folder holding existing work.

  ```bash
  mkdir my-project
  cd my-project
  git init
  jig init
  git status --short
  ```

  Review the generated files, then save this initial setup:

  ```bash
  git add .
  git commit -m "Set up Jig"
  ```

  If Git asks for an identity, set your name and email for this repository, then retry the commit:

  ```bash
  git config user.name "Your Name"
  git config user.email "you@example.com"
  ```

  For an existing repository, run only `jig init`, review the diff, and stage the setup files
  explicitly. Do not include unrelated changes in the setup commit.
</Accordion>

<Accordion title="For developers: what project setup adds">
  `jig init` adds `.ai/` (knowledge, configuration, scripts), skills in `.claude/skills/` and
  `.codex/skills/`, and entries in `.gitignore` and `.gitattributes`. It creates `AGENTS.md` and
  `CLAUDE.md` only when absent. It detects verification profiles from manifests such as
  `package.json`, `composer.json`, and `pyproject.toml`.

  `jig init` commits nothing. Commit the setup so teammates receive the same project copy of Jig.
  An empty project starts with the generic profile; stack-specific profiles follow when you choose
  the technology. Jig itself needs no Node.js, Python, or build step; your application may need them.
</Accordion>

## Jig first

Each row is a moment where a runtime offers its own way of doing the same thing. The middle
column is the way; the right-hand one is what it replaces.

| When you need to | Use | Instead of |
|---|---|---|
| Take on work someone described | the `jig-task` skill | starting to edit code straight away |
| Decide how much process the work needs | the risk test in the `jig-task` skill | reading a class off one word in the route table |
| File the work as a unit | `jig task new <id>` | the runtime's own background tasks (`spawn_task` in Claude Code): they open another session, not a task with a route, a workspace and consolidation |
| Get a branch for the task, or a tree of its own | `jig task start <id>`, or `jig task start <id> --worktree` | `git checkout -b`, `git worktree add` |
| Find what to read for the files you touch | `jig context --files <files>` | grepping `.ai/knowledge/`, or reading all of it |
| Write one of the task's documents | `jig task artifact write <id> <kind> --from <file>` | your editing tools on a path under `.ai/workspace/` |
| Show the work is done | `jig verify` | running the test commands yourself |
| Reach a commit and a pull request | `jig task ship <id> --message-file <file>` | `git commit`, `gh pr create` |

Keep this table short: eight rows get read; twenty stop being read, exactly as prose does. A
session to-do list (`TodoWrite` and the like) is deliberately absent — it is a draft for one
session, not a unit of work, and nothing here replaces it.

## Read first

- `.ai/knowledge/GLOSSARY.md` — canonical terms; use them in code and docs.
- `.ai/knowledge/RULES.md` — rules and invariants; never violate them.
- `.ai/knowledge/ARCHITECTURE.md` — domains, boundaries, dependency directions.
- `.ai/knowledge/adr/` — accepted decisions; propose a new ADR instead of silently
  contradicting one.

Do not read all of `.ai/knowledge/` up front. Ask the scripts for what is relevant:

```
.ai/scripts/jig context --files <changed files>
```

## Workflow

Start work with the `jig-task` skill; it classifies the task by risk and names the route.
Stage skills can also be used directly: `jig-analyze`, `jig-implement`, `jig-review`,
`jig-verify`, `jig-consolidate`, `jig-architecture-review`.

Three skills sit outside the task routes. Two populate knowledge rather than change
code: `jig-map` proposes per-domain knowledge, and `jig-accept` decides what is proposed.
A proposed document is invisible to `jig context` until a human accepts it, so knowledge
someone wrote but nobody agreed to reaches no agent — `jig status` reports the count on
its `proposals:` line, and `jig knowledge proposed` lists it. The third, `jig-idea`, works
before a route: it stress-tests an idea and keeps the result as a specification with a
roadmap under `.ai/specs/<id>/`. A specification is a plan, not knowledge, so `jig context`
never resolves it — `jig status` counts specs on its `specs:` line, and `jig spec list`
lists them with their roadmap progress. A spec released once, at the end, is built on an
epic branch (`jig spec epic`): its tasks are cut from the epic and their pull requests go
into it.

`jig-autopilot` runs one task's route without waiting between stages and stops only where a
human is needed; the route, the gates and `agent.git` stay what they are.

`jig-setup` asks a person, one question at a time, how far their agent may go on its own and
writes the answers to their gitignored `.ai/config.local.yaml` through
`jig config set --local`; it never writes `.ai/config.yaml`.

**Three questions decide the class**, asked about this change being wrong after it shipped:
what takes it back; how far the mistake reaches — this repository, or users, money, somebody
else's system; and who finds it — a test and the next run, or the person it hurt. The class is
the **highest** one whose answers fit; the full test, with examples, is in the `jig-task` skill.

| Class | Route |
|---|---|
| T0 trivial | implement, verify, consolidate |
| T1 local | analyze, implement, verify, consolidate |
| T2 structural | analyze, plan, implement, review, verify, consolidate |
| T3 architectural | discover, design, human gate, implement, architecture review, verify, consolidate |
| T4 critical | discover, specify, alternatives, design, human gate, implement, independent review, verify, consolidate |

Every route ends in consolidation, and a task with a workspace ends it in two records.
Before the commit, the knowledge decision — `NO_DURABLE_KNOWLEDGE` included — is recorded
with `jig task set <id> knowledge_consolidated true`. After the change has landed, when
`jig status` counts it under `needs consolidation`, the task is closed with
`jig task set <id> status consolidated`. A merge alone never closes a task.

Risk sets the floor: a one-line change to authentication is not trivial. When a task
turns out bigger, re-classify with `jig task set <id> class Tn` and run the stages the
new class requires.

## 3. Let the agent learn the project

```text Send to your agent
Set up Jig for this project. Explain what you find in plain language
and show me the project notes you write.
```

For existing code, the agent documents what the project does and the rules it follows. For an
empty project, it offers to work through your idea first. You review its understanding before
building on it.

## Keep Jig up to date

Updating is two separate steps, because updating the tool on your machine must never change a
project behind your back.

```bash
jig self-update          # the tool on your machine: to the newest release, never backwards
jig upgrade --dry-run    # in a project: what would change
jig upgrade              # in a project: update its copy of Jig
```

`self-update` refuses a checkout with uncommitted changes and changes no project. `upgrade` fetches
nothing: it copies from the Jig on your machine, updates only files Jig installed and you did not
edit, removes the ones Jig no longer ships unless you edited them, keeps and reports the edited ones, and never touches project knowledge or configuration.
In `AGENTS.md` it updates one thing — the section between `<!-- jig:begin -->` and
`<!-- jig:end -->`, and only while that section is still exactly what Jig last wrote there, so
improvements to Jig's own instructions reach your project without you doing anything. Edit inside
those markers and Jig keeps your version instead. `jig status` tells you when the project's copy is older than the tool. Review the
diff and commit it.

Run `jig doctor` any time something seems off: it checks the tool, the project and the agent
instructions, one line each, with a fix for every warning.
