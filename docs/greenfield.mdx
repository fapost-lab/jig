This guide uses a booking app for a yoga studio as an example. Replace it with your own idea.
By the end, you will have a plan and know how to ask the agent to build and show the first part.

<Note>
  **Before you begin:** finish [installation and project setup](/install). Open that project folder
  in your AI coding app. Everything in a “Send to your agent” box below goes in its chat.
</Note>

## 1. Describe your idea

```text Send to your agent
I have an idea: a booking app for a small yoga studio.
Visitors should see the class schedule and reserve a place.
I have no programming experience. Help me shape the first version,
ask one question at a time, and explain your recommendations simply.
```

The agent helps you work out who will use it, what problem it solves, and which features can wait.
It also recommends the technology and structure of the project, explaining the trade-offs.

**Your part:** answer from real life. How many classes are there? Can a visitor cancel? Does the
first version need payments, or is reserving a place enough?

<Tip>
  Start with one useful journey: “A visitor finds a class and books it.” You can add accounts,
  reminders, and payments later as separate tasks.
</Tip>

**Before moving on:** you should be able to describe the first version in a few sentences and say
what it leaves out. Ask the agent to show you its plan and correct anything it misunderstood.

<Accordion title="For developers: the specification and roadmap">
  The agent uses `jig-idea` to question the idea, stress-test assumptions, and compare alternatives.
  You choose easy, normal, or deep exploration; deep includes an independent agent's challenge.

  It records the result in `.ai/specs/<id>/`: `spec.md`, `architecture.md`, `stack.md`, and
  `roadmap.md`. The roadmap holds phases, dependencies, parallel waves, and `fog:` for work that
  cannot yet be stated precisely. Replace its example items before using it.

  Specifications are committed plans. They are not resolved as project knowledge, so future
  intentions do not become claims about implemented behaviour. To move a spec to another
  project, copy its `.ai/specs/<id>/` folder there.
</Accordion>

## 2. Give future sessions the same plan

```text Send to your agent
Set up the project's knowledge from the spec we agreed on.
Show me what future AI sessions will need to know about this project.
```

The agent writes down the project's purpose, terms, structure, and rules. Read what it shows you
and correct mistakes: these notes help the next session work from the same decisions.

**Before moving on:** the agent should have recorded the agreed decisions and clearly marked
what has not been built yet.

<Accordion title="For developers: how decisions become knowledge">
  `jig-init` carries decisions into `.ai/knowledge/`: terms into `GLOSSARY.md`, boundaries into
  `ARCHITECTURE.md`, invariants into `RULES.md`, and decisions with alternatives into ADRs.
  Component contracts become conventions. Planned architecture is labelled **Intended — not built yet**.

  The chosen stack determines verification profiles. Until the project's tools and manifests exist,
  those checks report skips, not passes. The task that implements a part updates its intended status.
</Accordion>

## 3. Choose the first thing to build

```text Send to your agent
File the tasks for the first phase of the roadmap.
Show me which task gives us the first result I can try, and its task ID.
```

Filing tasks makes a to-do list; it does not start building. When the first task is clear, use its
actual ID in your next message:

```text Send to your agent
Start task <task-id>. When it is ready, show me how to open it
and the steps I should try to check that it works.
```

Replace `<task-id>` with the ID the agent showed you. For our booking app, the first result might
be a class schedule; reservations could be the next task.

<Info>
  If the agent asks you to approve a design, read it before saying yes. You can ask it to explain
  a choice, reduce the scope, or change the plan. You do not need to approve something you do not understand.
</Info>

<Accordion title="For developers: tasks, branches, and releases">
  The agent classifies each task by risk and links it to the spec. Tasks normally branch from
  the project's main branch. If the product will be released once at the end, the agent discusses
  an **epic branch** with you while shaping the roadmap. Its tasks branch from the epic and their
  pull requests target it; the main branch receives the combined work when the epic is merged.

  `jig spec epic <id>` creates that branch once the spec is on the main branch. The roadmap records
  the release's version bump. `jig spec ship` follows your [Git permissions](/agent-ships#specs-and-epics).
  Finishing the epic asks about any remaining items, fog, or open questions before retiring the spec.

  At consolidation, completed tasks check their roadmap items in the same change as the implementation.
  See [manual control](/manual-control) for task commands and [autopilot](/autopilot#running-a-whole-phase)
  for running a whole phase.
</Accordion>

## 4. Try the result and give feedback

Follow the agent's instructions to open the project. For a website this will usually be a local
preview: a page on your computer that other people cannot yet visit.

Describe what happened and what you expected:

```text Send to your agent
I can see the schedule, but I can't tell which classes still have places.
Show the available places next to each class, then tell me how to check it.
```

Before calling the first version ready, ask:

```text Send to your agent
What works now, what did you test, and what is still missing?
What needs to happen to save this work and let other people use it?
```

<Warning>
  Passing checks does not mean a project is ready for real customers. Payments, personal data,
  and public access need their own review. Ask the agent to identify the remaining work before launch.
</Warning>
