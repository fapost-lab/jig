Use this page to look up the terms an agent mentions. You do not need to learn them before
[starting a project](/greenfield).

| Term | In plain language |
|---|---|
| Agent | The AI doing the work inside your coding app. |
| Runtime | The coding app, such as Claude Code or Codex. |
| Task | One piece of work, with a goal you can check. |
| Skill | Instructions the agent follows for a kind of work. |
| Knowledge | Project rules and decisions saved for future tasks. |
| Context | The information available to the agent while it works on a task. |
| Specification | A plan for work that has not been built yet. |
| Human gate | A point where the agent needs your approval before continuing. |
| Consolidation | Deciding what a finished task should leave in the project's notes. |

## How Jig builds context for a task

**Project knowledge is organized for selective reading.** The agent does not need to load the
whole handbook every time you ask for a change. Jig helps it find the rules and decisions that
apply to the work in front of it, while keeping other relevant material discoverable.

Think of a well-organized reference library: a few essential rules stay on the desk, the books
needed for the task are opened, and a short catalog points to anything else worth checking.

<Steps>
  <Step title="Keep the shared foundations">
    The project's glossary, architecture, and core rules are always required. A focused task
    still needs to respect the whole project's basic constraints.
  </Step>
  <Step title="Find what applies to this task">
    The agent identifies the files and areas it is working on. Jig uses document metadata to
    select the knowledge required for those files, topics, and the current stage of work.
    If a selected document depends on another, that document is included too.
  </Step>
  <Step title="Read the essentials; browse the rest when needed">
    Jig returns paths to the required documents and a compact catalog of other potentially
    relevant material. The agent reads the required documents and can open additional ones
    from their catalog entries. Listing a document does not load its full text.
  </Step>
  <Step title="Update the selection as the work grows">
    When the agent reaches another part of the project or moves to a new stage, it asks for
    context again. Newly relevant documents join the reading list. Documents changed since
    the agent acknowledged reading them need another look.
  </Step>
</Steps>

### An example: changing bookings

Suppose you ask: **“Stop people booking a class that is already full.”** With knowledge mapped
to the relevant areas, the reading list could look like this:

| Material | How it is used |
|---|---|
| Project glossary, architecture, and core rules | Always required. |
| Rules that apply to booking files | Read in full for this task. |
| A decision those booking rules depend on | Included with the rules. |
| Other booking documents | Discoverable through short catalog entries unless selected as required. |
| A reporting guide with no matching scope or dependency | Its body is not required for this task. |

If the work turns out to affect payments too, the agent expands the selection. It does not keep
working with a reading list that only covers bookings.

### Why this can save tokens

Tokens are the pieces of text the AI processes. Loading fewer unrelated documents can use fewer
input tokens and leave more context space for the task, its code, and the conversation.
The catalog helps the agent discover additional knowledge without reading every document in full.

<Note>
  This is selective loading of **project knowledge**, not a cap on everything the AI reads.
  Conversation history, code, tool results, and instructions from the coding app also use context.
  Savings depend on the task, document sizes, and the agent's reading choices; Jig does not measure
  token savings or promise a percentage.
</Note>

<Accordion title="For developers: selection rules, stages, and reading records">
  `jig context resolve` selects documents deterministically from metadata. It makes no AI call
  and returns paths for the agent to read, rather than injecting document bodies into the model.

  | Metadata | Effect |
  |---|---|
  | `load: always` | Requires the document for every resolution. |
  | `load: domain` | Requires it when one of its declared domains is selected. |
  | `load: matched` (default) | Requires it for matching file paths or topics, an explicit ID, or a matching stage within an entered domain. Domain membership alone makes it discoverable in the catalog. |
  | `requires` | Adds the selected document's dependencies transitively. |
  | `summary` | Supplies the short description in a catalog entry. |

  The catalog also includes active project-wide documents with neither paths nor domains.
  Proposed and retired knowledge is excluded from normal resolution. A directory name alone
  does not decide applicability: the document's metadata does.

  **Stage selection is additive.** `--stage` can bring in additional guidance for the stage;
  it never removes required globals, existing matches, or dependencies to make the context smaller.
  `--ids` explicitly selects a catalog document when the agent needs its full content.

  For example, in Jig's own repository, inspect what an edit to the introduction requires:

  ```bash
  jig context resolve --no-task --files docs/index.mdx --stage implement --catalog
  ```

  For a task with a workspace, `context acknowledge` records the hashes of documents the agent
  says it read. `context pending` identifies required documents that are new or changed;
  `context guard` fails while any remain unacknowledged. Unchanged documents keep their record
  across stages. This records a reading claim, not comprehension or continued presence in the
  model's context; it does not replace a handoff when an agent session changes.

  See [Manual control](/manual-control#ask-which-knowledge-applies) for task-based commands and
  [Under the hood](/under-the-hood#knowledge-and-what-an-agent-reads) for the limits of these records.
</Accordion>

## Risk classes and routes

Every piece of work gets a class from its risk — what it could break and how hard that is to undo
— never from how much typing it takes. The class decides the route.

| Class | Typical work | Route |
|---|---|---|
| **T0** trivial | Wording, formatting, an obvious documentation edit | implement → verify → consolidate |
| **T1** local | A contained change with an obvious solution | analyze → implement → verify → consolidate |
| **T2** structural | Several components, or an internal contract | analyze → plan → implement → review → verify → consolidate |
| **T3** architectural | Boundaries, dependencies, lifecycle semantics | discover → design → **human gate** → implement → architecture review → verify → consolidate |
| **T4** critical | Security, secrets, destructive operations, money | discover → specify → alternatives → design → **human gate** → implement → independent review → verify → consolidate |

**Risk sets the floor.** A one-line change to authentication is never T0. When work turns out bigger
than it looked, the agent re-classifies it and runs the stages the new class requires.

**At a human gate** the agent shows you the document itself — the design, and for T4 the
specification and the alternatives — word for word, with its own objections after it. It records
what you decided and does not implement until you approve. A summary is never what gets approved.

**Every route ends in consolidation**, even a typo fix: the task decides what the project should
remember, and records "nothing" explicitly when that is the answer.

## What a review leaves behind

A review does not end in an opinion. It ends in two records that the rest of the route has to
get past.

**Findings** — each problem the review found, written down with a severity: P0 breaks data,
security or a rule or decision the project recorded; P1 gives a wrong result on a path that will be used;
P2 and P3 are worth fixing but do not block. A P0 or P1 stops the task mechanically: while one
is open the agent cannot mark the task ready, cannot record what the project should remember,
and cannot commit or open the pull request. A fix alone does not clear it — a second review
confirms the fix. The other way out is a decision that it need not be fixed, and for a P0 or P1
that decision is a human's.

**The receipt** — what the review actually looked at: the code, the approved design, the list
of findings. If any of it changes afterwards, the review no longer describes the change, and
the task stops again until it has been reviewed once more. A T4 task cannot be finished without
a receipt at all.

Both are what keeps "reviewed" from meaning "someone said it was fine earlier"
([Working with tasks](/working-with-tasks#review-findings)).

## How far the agent goes

Whether a finished task stays in your working tree or arrives as an open pull request is a
setting, `agent.git`, with five levels: `none`, `commit`, `push`, `pr`, `merge`. It is
**personal**: it lives in a gitignored file, it changes what your agent does in your copy of
the project, and putting it in the shared file does nothing — one person's trust can never be
switched on for the whole team.

The levels are enforced by a script rather than by the agent's good intentions: `jig task ship`
commits only what was staged, never force-pushes, never skips your Git hooks, refuses before
the task's knowledge decision is recorded, and merges only at `merge`, only on green checks,
and never past your repository's own branch protection
([Letting the agent ship](/agent-ships)).

## Running without you

The routes above assume you are there between stages. Two things change that.

**Autopilot** runs one task's route end to end without waiting: same stages, same gates, same
rules. Two differences — the review is done by a *second* agent, which did not write the code,
and fixing is capped at two attempts per run, after which Jig itself refuses a third and the
run stops rather than circling. A run stops only where a human is genuinely needed: a design to
approve, a problem it could not fix, a decision nobody has made, a step that would destroy
something. It ends with a report of every stage, every repair and every stop
([Autopilot](/autopilot)).

**Unattended** is for when those questions are not yours to answer. Where a run would stop, it
takes the careful, reversible option instead and writes down in the pull request exactly what it
chose without you; where it could not finish, it opens a draft pull request that says so. It
never dismisses a serious finding, never skips the review, and merges only what your CI proved
([without stops](/autopilot#without-stops)).

A run can also take a whole **phase** of a roadmap instead of one task. The agent becomes a
coordinator: it files the phase's wave of items, gives each task its own worktree and its own
agent, and those agents build at the same time while the coordinator ships them, keeps the
merge queue and starts the next wave. It writes no code itself. This is the one place Jig runs
several agents at once, and it needs an [epic branch](#epics) and the right to open pull
requests ([running a whole phase](/autopilot#running-a-whole-phase)).

## Project knowledge

`.ai/knowledge/` holds what an agent must know to change the project well — the *why* that the code
cannot say. It is committed with the code and reviewed in pull requests.

| Document | Holds |
|---|---|
| `GLOSSARY.md` | Canonical terms — the words a newcomer would get wrong. |
| `ARCHITECTURE.md` | Domains, boundaries, which way dependencies may point, key flows. |
| `RULES.md` | Invariants and rules, each with its source. |
| `adr/` | Decision records: what was decided, which alternatives lost, and why. |
| `conventions/` | How code is written in a part of the project — including what the implementations of a component boundary may, must and must not do. |
| `features/` | How a part of the product behaves. |
| `domains/<name>/` | Knowledge packs for one domain: overview, glossary, rules. |
| `sources/` | Pointers to documents the project already had, linked in place ([Existing project](/brownfield)). |

### Only what is relevant reaches the agent

The agent uses the [context selection process above](#how-jig-builds-context-for-a-task) to find
what it needs. The three global documents remain required; other documents are selected through
their metadata or discovered in the catalog. As the task's scope changes, the selection grows
with it. This structure is what makes project knowledge usable without loading the whole library.

### Proposed knowledge waits for a human

Knowledge an agent inferred — a domain map, a linked document, a copied rule file — is created as
**proposed**. It sits at its real path and shows in the diff, but no agent receives it until a human
accepts it. Rejecting records the decision rather than deleting the document. Knowledge an agent
writes at the end of a task is reviewed in the pull request like the code.

### Knowledge that drifted

Each document records when it was last reconciled with the code. When the files it describes changed
after that, it is reported as stale; when a linked document of your own changed since it was
approved, `jig status` says so until a human has looked at the change.

## Specifications

A specification is a plan for work bigger than one task — a feature of tens of tasks, or a new
project. It lives in `.ai/specs/<id>/`: the idea, the stress test it went through, the decisions,
open questions, and a roadmap of phases and items. It is committed and reviewed like any file, but it
is **not knowledge**: no agent working on the code reads tomorrow's plan as a description of today's
system. Its progress is its roadmap's checkboxes, checked by the tasks that deliver the items.

### Epics

A specification whose phases give a user nothing on their own is released once, at the end. It gets
an **epic branch**: its tasks branch from the epic and their pull requests go into it, and the main
branch receives the whole feature in one pull request. Finishing the epic lists what is still open in
the specification and asks about each item before the specification is retired.

## Cleanup

Task workspaces are temporary and are cleaned up without anyone remembering to:

- a task whose change was merged is flagged until it is closed; once closed, its workspace moves to
  `.ai/runtime/trash/`, and is deleted from there after a retention period (7 days by default);
- a task whose remote state cannot be determined keeps its workspace;
- an abandoned task's workspace goes to the trash after 14 days, whatever its remote state;
- old active tasks are only reported, never deleted for their age.

Housekeeping is started by a Claude Code session hook or a scheduler you choose
([Configuration](/configuration#when-housekeeping-runs)); the agent also shows you, at the start of
a session, which merged tasks wait to be closed.

## Measurement

`jig measure` reports, when you ask:

- **knowledge** — how many documents, how many stale, unreviewed or without code to describe;
- **process** — how many tasks of each class, and how they ended;
- **change** — how big the change each class produced was.

Everything is derived from what is already in the repository and the local task records; nothing is
sent anywhere. It cannot price the work: tokens, time and whether a human gate was passed are not
recorded anywhere, and the report says so.
