---
title: "Reading Jig as data"
description: "Read your project's tasks, specs and what needs you from a script, a bot or a dashboard as JSON, without parsing text and without touching the network."
---

Jig's commands print text for a person. A program — a CI step, a chat bot, a dashboard such as
[Jig UI](https://jig-ui.fapost.in) — can ask for the same answer as JSON instead, by adding
`--json`. Today `jig task list`, `jig task artifacts`, `jig task artifact read`, `jig spec list`, `jig status`,
`jig queue list`, `jig queue next`, `jig config keys`, `jig knowledge proposed`, `jig knowledge sources`, `jig knowledge read` and
`jig writes` offer it, and `jig queue`, `jig task new`, `jig upgrade`, `jig config set|unset`, `jig spec item`
and `jig knowledge accept|reject|reviewed` answer in it when they write; more commands will, in the
same form.

```bash
jig task list --json
jig task list --json --all
jig task artifacts <id> --json
jig task artifact read <id> plan --json
jig spec list --json
jig status --json
jig queue list --json
jig knowledge proposed --json
jig knowledge sources --json
```

<Info>
  A `--json` read never touches the network. It reads files on your disk and asks Git about your
  local repository; it never calls `gh` or fetches. You can run it as often as you like, in many
  projects at once, without running into a forge's rate limits.
</Info>

## The envelope

Every `--json` command prints exactly **one line**: a JSON object called the envelope. On success
it carries the answer in `data`:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-15T12:00:00Z","data":{"tasks":[...],"hidden":0,"housekeeping":null}}
```

When the command refuses — an unknown flag, a project without Jig — it still prints one line, with
`error` in place of `data`, and exits with a non-zero status:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-15T12:00:00Z","error":{"code":"usage","message":"task list: invalid status: bogus"}}
```

- `schema` is `1`. It changes only when a field is removed, renamed or changes type. New fields
  can appear at any time without it changing, so ignore the fields you do not know.
- `revision` is a number that changes whenever Jig writes anything in the project — a task, its
  documents, a spec, knowledge, a housekeeping run — in this checkout or any of its worktrees. If it
  is the same as on your last read, Jig changed nothing; if it differs, read again. It is `0` before
  Jig's first write, and only its changes mean anything: compare it, do not do arithmetic with it.
  A file changed by hand or by git — your `git pull`, or the branch Jig checks out after a merge —
  does not change it: watch the files too if that matters to you.
- `generated_at` is when the read started, in UTC.
- `error.code` says why the command refused, in a word your program can act on (below).
  `error.message` is the same text the command prints after `jig: error:`, meant for a person.

Warnings meant for a person still go to stderr, so stdout always holds just the envelope.

### Why a command refused

Act on `error.code`, never on the wording of `error.message`: codes stay as they are, messages may
be reworded.

| `error.code` | What happened |
|---|---|
| `usage` | the command was called with an argument it does not take, or with a value it does not accept — check how your program calls it |
| `not-a-repository` | it ran outside a Git repository |
| `not-initialised` | the repository has no Jig yet; `jig init` sets it up |
| `stale-revision` | a write carried a `revision` that is no longer current: something changed since your program read it. Nothing was written — read again, and show the person the conflict |
| `not-found` | the task or epic named does not exist, is not in the queue where the command needs it, the task has no such document yet (`jig task artifact read`), or the knowledge document named does not exist (`jig knowledge read`) or links no source (`jig knowledge sources --diff`). For a roadmap edit: the spec it names is neither on its branch nor on the base, the phase or item is not in the roadmap on that branch, or the task it would file does not exist. Also `jig writes ship` with nothing waiting |
| `already-exists` | what the command would create is already there: a task with that id, a roadmap item with that text, an item that names a task. Nothing was written |
| `git-not-allowed` | [a write on a branch of its own](#writes-on-a-branch-of-their-own) was asked for at `agent.git: none`, where Jig commits nothing. Nothing was written; the message names the setting |
| `write-busy` | another such write is running in this project. Nothing was written — try again in a moment |
| `branch-checked-out` | the write's branch is checked out somewhere, and Jig never moves a checkout. Nothing was written; the message names where |
| `branch-diverged` | the write's branch and the one on the remote have diverged. Nothing was written, and nothing is forced |
| `branch-has-other-commits` | the write's branch has commits here that no write made and the remote does not have: yours, and a write does not publish them. Nothing was written; the message names the branch |
| `base-not-on-origin` | the write's base is not on the remote, at `agent.git: push` or above: a branch cut from it would carry out whatever is on it. Nothing was written; push that base yourself |
| `write-still-waits` | an earlier edit of the same spec, or of knowledge, still waits where this one cannot go: into another base, because an epic opened or finished since, or as edits that never reached the remote above ones whose pull request was closed or whose branch was deleted there. Nothing was written; the message names the branch and what to do |
| `tree-in-the-way` | an unfinished write left something at Jig's tree that git will not remove. Nothing was written, and trying again does not help: delete the path the message names |
| `commit-refused` | Git refused the commit, usually a hook of the project; the message says what it said. This edit was not committed; an earlier one already waiting on the branch still waits |
| `epic-missing` | the spec is built on an epic branch that is neither here nor on the remote. Nothing was written |
| `not-linkable` | the task cannot be linked to the roadmap item, or the item is done. Nothing was written |
| `not-proposed` | the knowledge document is not a proposal, nor, for `reject`, a stub whose linked file changed since it was approved: it was decided already, perhaps on a branch that still waits. Nothing was written |
| `not-on-base` | the knowledge document, or the change to the file a stub links, is in your checkout but not on the base the decision is judged on: not committed, or not pushed. Nothing was written — push it first |
| `not-on-branch` | the knowledge document, or that change, reached the base after the branch the decisions wait on was cut. Nothing was written — decide it once the decisions waiting there have landed |
| `source-missing` | the file a knowledge stub links is missing or not tracked. Nothing was written |
| `not-closable` | the task you asked to close is not one Jig offers to close: its knowledge decision is not recorded, or its pull request is not merged. Nothing was written — show the person the message, which is the reason |
| `not-paused` | the task you asked to resume is not paused: somebody resumed it first. Nothing was written — read again |
| `wrong-checkout` | the task's pause put work aside in a stash, and the stash can only be applied where the task's branch is checked out. Nothing was written — show the person the message, which names that place |
| `stash-conflict` | the stash the pause put aside did not apply, or applied with conflicts that are not resolved yet. The task stays paused and the stash is kept — the person resolves it in the task's checkout and resumes again; a stash already applied with conflicts is not applied a second time |
| `upgrade-blocked` | `jig upgrade` would not start here and changed nothing; the message names every reason and what to do |
| `unknown-key`, `not-local`, `invalid-value`, `secret-key` | `jig config set --json` refused a key or value: a name Jig does not read, a key only the team's `.ai/config.yaml` answers for, a value the key does not accept, or a secret on a command line. Nothing was written |
| `failed` | anything else: the message says what |

New codes may appear, for refusals that today read `failed`. Treat a code you do not know as
`failed`. Whatever the code, the command exits with a non-zero status.

## Tasks

`jig task list --json` lists the same tasks as `jig task list` with the same flags: unfinished ones
by default, everything with `--all`, one status with `--status <status>`. `data.hidden` says how many
finished tasks were left out, and `data.archived` how many of those are archived.

A task Jig put away has `status: "archived"`, and three fields say how: `archived_at` (a date),
`archived_reason` (`abandoned`, `stale`, `manual` or `absorbed`) and `archived_from` (the status before); they are
`null` on every other task. The value is new, but schema 1 stands: archived tasks are left out of the
default selection, so a program appears to see one only when it asks with `--status archived` or
`--all`. To show an archive column, ask for `jig task list --json --status archived`; an archived
task offers only the `unarchive` action.

Merging tasks (`jig task merge`) adds four more fields to every task: `absorbed_into` (the receiving
task's id, or `null`) and the arrays `absorbs`, `absorbs_partly` and `partly_in` (empty when there is
nothing to say). A task absorbed whole is archived with `archived_reason: "absorbed"`. These are
additions, so schema 1 stands.

Each task carries what Jig knows about it:

```json
{
  "id": "booking-message",
  "class": "T1",
  "status": "active",
  "issue": null,
  "goal": "Show the booking reference in the confirmation message.",
  "knowledge_consolidated": false,
  "paused": false,
  "created_at": "2026-10-14",
  "updated_at": "2026-10-15",
  "branch": "task/booking-message",
  "base_branch": "main",
  "worktree": {"path": "/home/me/shop.worktrees/booking-message", "uncommitted": 2},
  "gate": null,
  "autopilot": null,
  "pull_request": {
    "url": "https://github.com/me/shop/pull/42",
    "state": "open",
    "ci": "green",
    "fetched_at": "2026-10-15T09:00:00Z"
  },
  "housekeeping_flags": [],
  "actions": [
    {"id": "start", "command": "jig task start booking-message", "offered": false, "reason": "task start: already started on task/booking-message; ..."},
    {"id": "pause", "command": "jig task pause booking-message", "offered": true, "reason": null},
    ...
  ]
}
```

A fact Jig does not have is `null`: `branch` is `null` for a task not started yet, `goal` for a task
whose `## Goal` holds nothing but an HTML comment such as the template's `<!-- … -->` hint, `gate`
for a task without a design approval step, `autopilot` for a task that never ran on autopilot. The
flags are the ones the last `jig housekeeping` run raised and that still apply, for example
`needs-consolidation` for merged work nobody has closed yet; `data.housekeeping` says when that run
was.

`pull_request` says whether the pull request is `open`, `merged` or `closed`, and how its checks
went: `green`, `red`, `pending`, or `none` when no check ran. Both are what the last `jig
housekeeping` heard from the forge, at `fetched_at`; the read itself never asks. When housekeeping
has not run, or the forge did not answer, they are `null` or as old as `fetched_at` says — run
`jig housekeeping` to refresh them. Checks are asked only for open pull requests, and GitLab's list
carries none, so there `ci` is `null`.

## What a person may do next

`actions` lists what a person can do with the task right now, so a dashboard can show the right
buttons without knowing Jig's rules. Every task carries the same fourteen actions, in the same order:

| `id` | What it does |
|---|---|
| `start` | Start a task that was filed for later; refused for a T3 or T4 task whose `task.md` has no goal |
| `pause`, `resume` | Set the task aside, and pick it up again |
| `request-pause`, `cancel-pause-request` | Ask a running task to pause when it finishes its current stage, and take the request back |
| `approve-gate` | Approve the design of a T3 or T4 task waiting at its gate |
| `answer-stop` | Answer an autopilot run that stopped to ask you something |
| `set-class` | Change the task's class |
| `ship` | Commit, push and open the pull request, as far as your settings let the agent |
| `close` | Close a task whose work has landed |
| `abandon` | Give the task up; its `command` asks for `--reason <text>` when the task is linked to a spec |
| `archive` | Put an active, ready or abandoned task away, without deleting it |
| `unarchive` | Bring an archived task back to the status it had |
| `reopen` | Take back an abandoned task |

`offered` is `true` when Jig would accept the action now, and `command` is the Jig command that does
it, with the values you supply written as `<text>`, `<Tn>` or `<file>`. When `offered` is `false`,
`reason` says why, in the same words the command itself would refuse with.

Jig judges the task's own state. A few things it cannot know until the command runs: whether you are
in the right place (run `resume` and `ship` in the task's worktree when it has one), whether there is
anything to commit, and whether the forge agrees. `close` trusts what the last `jig housekeeping`
heard about the pull request: until it has seen the merge, `close` stays unavailable.

More actions may appear later; ignore the ones you do not know.

## Specs

`jig spec list --json` lists the same specs as `jig spec list`, each with its roadmap as data: its
phases, the items of each phase, and how far it has come.

```json
{
  "id": "booking",
  "title": "Booking flow",
  "missing_files": [],
  "release": "minor",
  "epic": {"branch": "epic/booking", "state": "open", "checked_out": false, "missing": false, "ref": "refs/remotes/origin/epic/booking"},
  "progress": {"done": 1, "total": 3, "filed": 1, "fog": 1},
  "phases": [
    {
      "phase": 1,
      "title": "Book a table",
      "done": 1, "total": 3, "filed": 1, "fog": 1,
      "items": [
        {"text": "`booking-form` — the form", "checked": true, "done": true, "task": "booking-form", "fog": false},
        {"text": "`booking-message` — the confirmation", "checked": false, "done": false, "task": "booking-message", "fog": false},
        {"text": "fog: reminders by text message", "checked": false, "done": false, "task": null, "fog": true}
      ]
    }
  ]
}
```

`progress` is the same count `jig spec list` prints, and the sum of the phases. Each item says
whether it is checked, whether it counts as done, which task it names, if any, and whether it is
still fog. An item counts as done when it is checked, or when the task it names is known on this
machine to have merged — closed, or seen merged by the last `jig housekeeping` — even before its
checkbox reaches the branch you read.

A spec built on an epic branch keeps its roadmap there. When you read it from another branch, the
phases come from the epic's branch as your repository last fetched it — `epic.ref` names it — and
when that branch is nowhere on your disk, `epic.missing` is `true` and `progress` is `null`.
`release` is the version level the epic will be released at, or `null` when none was recorded.

## What needs you

`jig status --json` lists what needs a person in the project — the same items, in the same order,
as the "Needs you" cards on the status page (`jig status --open`), because both are built from one
list. An empty `attention` means nothing needs you.

```json
{
  "attention": [
    {
      "kind": "autopilot-stopped",
      "subject": {"type": "task", "id": "booking-message"},
      "tasks": ["booking-message"],
      "title": "Autopilot stopped and is waiting for you",
      "detail": "stopped 5 min ago: Which payment provider should the refund use?",
      "todo": "Answer the agent in this task's session; it resumes the run.",
      "url": null
    }
  ],
  "housekeeping": {"ran_at": "2026-10-15T09:00:00Z", "forge": "github", "stale": false},
  "knowledge_counts_at": "2026-10-15T08:00:00Z"
}
```

A program acts on `kind` and `subject`; `title`, `detail` and `todo` are the words the page shows a
person, and may be reworded. The kinds cover a stopped autopilot run (`autopilot-stopped`, or
`phase-stopped` for a phase run, whose `tasks` lists every stopped task), a design at its gate
(`gate-waiting`, `gate-changed`), a finished task waiting for your git step (`git-step`), pull
requests to review, merge or close (`pull-request-waiting`, `pull-request-was-open`,
`pull-request-of-abandoned-task`), what housekeeping flagged (`needs-consolidation`, `wrong-base`,
`closed-unmerged`, `worktree-kept`), knowledge to decide (`knowledge-proposed`, `sources-changed`)
a newer jig (`release-available`), and a project whose own Jig is older than the one on your machine
(`upgrade-available` — the item a program lists to show which projects need `jig upgrade`; it alone
carries `"versions": {"from": "0.32.0", "to": "0.33.0"}`, the project's Jig and your machine's),
and an upgrade that ended in a pull request: `upgrade-pull-request-waiting` while it is open,
`upgrade-pull-request-merged` once it is merged but your base branch here still has the old Jig.
Both carry `"pull_request": {"branch", "base", "state", "fetched_at"}` and `"versions": {"to"}`, and
while one stands for your machine's version or a newer one `upgrade-available` is not listed: what
the project needs is the merge and `jig upgrade --land`, not a second upgrade. One for an older
version, such as a pull request nobody merged or closed, does not hide the newer upgrade.

Pull request items are as old as the last `jig housekeeping` run; `housekeeping.stale` is `true`
when that run is older than your housekeeping cadence or the forge did not answer, so one may be
missing. The knowledge counts are the ones the last full `jig status` took for the page, at
`knowledge_counts_at`.

## The queue

The queue holds the priority, order and dependencies of tasks and epics, one per project, shared
by every worktree. `jig queue list --json` (or `jig queue --json`) reads all of it:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"items":[
  {"ref":"epic:booking","kind":"epic","id":"booking","level":null,"position":100,"priority":0,"depends_on":[]},
  {"ref":"task:booking-form","kind":"task","id":"booking-form","level":"epic:booking","position":100,"priority":null,"depends_on":[]},
  {"ref":"task:booking-message","kind":"task","id":"booking-message","level":"epic:booking","position":200,"priority":1,"depends_on":[{"on":"task:booking-form","reason":"Quotes the form"}]}
]}}
```

`items` is in the queue's order: the top level (`level` `null`) by `position`, then each epic's
tasks under their `level`. An empty queue is `"items":[]`. An item is the same object a write
below answers with, so a board renders both with one piece of code.

The queue holds order, not the tasks themselves: read it together with `jig task list --json`
and join a `task` item to a task by `id`, and an `epic` item to `jig spec list --json` by the
spec's `id`. All of them carry the same `revision` when nothing was written between the reads, and
the one you send with a change is the `revision` of the queue read you showed. An item whose task
is finished, archived, or gone, stays in the queue until it is removed; it has no match in the default task
list, so join against `jig task list --json --all` or show it as it is.

### Which task is next

`jig queue next --json` answers what the queue advises, so a board needs no rules of its own. It
reads the queue, the tasks' state and the last `jig housekeeping` run, never the network, and
changes nothing:

```json
{"schema":1,"revision":1792693064,"generated_at":"2026-10-22T18:17:22Z","data":{"next":{"ref":"task:booking-form","kind":"task","id":"booking-form","level":null,"position":100,"priority":1,"started":true},"reason":null,"waiting":[{"ref":"task:booking-message","on":"task:booking-form","state":"unknown","reason":"The message quotes the form"}],"taken":[],"not_queued":1}}
```

`next` is the task to take, or `null` with a `reason` (`waiting`, `taken`, `paused` or `empty`)
when there is none. `taken` lists each candidate another session is working on, with the
`checkout` it works in, `since` when and `idle_seconds` since it was last active; such a task is
never advised. `waiting` lists each dependency that holds a candidate back, in `state` `open`, `broken`
(it never ends; drop it with `jig queue undepend`) or `unknown`. `not_queued` counts the active
tasks outside the queue. The fields are in [the schema](https://github.com/fapost-lab/jig/blob/main/schemas/json.md).

## Changing the queue

A program changes the queue with the same commands a person uses, adding `--json` and the
`revision` of the read it decided on:

```bash
jig queue move booking-message --after booking-form --revision 1792079790 --json
jig queue set booking-message --priority 0 --revision 1792079790 --json
jig queue depend booking-message --on booking-form --reason "Quotes the form" --revision 1792079790 --json
```

If anything changed in the project since that read — another person's drag, an agent's task
update — the write is refused with `stale-revision` and nothing is written: read again and let the
person decide again. Two programs that send the same revision cannot both land: at most one does,
and when a third write slips in between, neither.
A write that lands answers with the item as the queue now holds it:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"ref":"task:booking-message","item":{"ref":"task:booking-message","kind":"task","id":"booking-message","level":null,"position":150,"priority":0,"depends_on":[]}}}
```

The envelope's `revision` is taken before the write, so with `--revision` it is the one you sent;
the write raised it, so read again before the next change. A move moves one item, never the others: drag an item by sending one
`move`, not by renumbering the list. `position` is only for comparing within a `level` — the top
level (`null`) orders epics and tasks without an epic, and `epic:<spec-id>` orders that epic's tasks.

## Writes on a branch of their own

A person's checkout is usually on the default branch or on a task's branch, and another session may
be working in it. So a change to a roadmap, or a decision on knowledge, is not written there: Jig
commits it on a branch of its own, in a tree of its own that lasts as long as the command, and takes it
as far as your [`agent.git`](/configuration) allows. Nothing you have checked out moves or goes dirty.

```json
{"schema":1,"revision":1793825280,"generated_at":"2026-11-04T20:55:47Z","data":{"spec":"foo","item":{"id":"i-7d2bc8dc7707","text":"Export a page","checked":false,"task":null,"fog":false,"phase":2},"write":{"target":"spec:foo","branch":"spec/foo","base":"main","commit":"4354faecc647079ac9e77cc352e8d007374c250e","commits":1,"pushed":true,"pr":null,"merged":false,"committed":true,"level":"push","note":"agent.git is push: the pull request is yours"}}}
```

`write` says where it went: the branch, the commit, whether it was pushed, the pull request, whether it
merged, and in `note`, for a person, why it went no further. A push that failed is said there and is not
a refusal: the commit stands and waits, and `jig writes ship <target>` carries it on. At `agent.git:
none`, the default, these writes are refused with `git-not-allowed`: Jig commits nothing until you say
it may. **Edits in a row go on one branch and one pull request.** A write never merges, even at `merge`,
because a merge waits for CI: `jig writes ship <target>` does that when the edits are done.

Until the edit lands, it waits, and a read says where:

```bash
jig writes --json
```

```json
{"schema":1,"revision":1793825285,"generated_at":"2026-11-04T20:55:48Z","data":{"writes":[{"target":"spec:foo","branch":"spec/foo","base":"main","commit":"4354faecc647079ac9e77cc352e8d007374c250e","commits":1,"pushed":true,"pr":null,"merged":false}]}}
```

`jig spec list --json` gives each spec `waiting`, with the roadmap as it is on that branch, and
`jig knowledge proposed --json` gives each proposal one with what was decided. It stops waiting once
the commits are on its base **as of the last fetch**, since a read never fetches.

A branch left behind stays where it is: when it merged by squash, its pull request was closed or it
was deleted on the remote, the next edit takes a new name such as `spec/foo-2`. A commit above what a merged pull request held
keeps its name and waits for a new one. When you are on the
branch yourself, or another worktree is, the write is refused with `branch-checked-out`, and the
message says where: finish there or switch away. When the branch has commits of yours that the remote
does not have, the write is refused with `branch-has-other-commits`: push or merge them, or move them
off. A write starts from the remote's base, so what you have not pushed to your own `main` stays out
of it. What the remote holds is what it says it has: a branch deleted there counts for nothing, pruned
or not. `jig writes ship` sends nothing of a pull request that was closed unmerged or merged with those
edits, or of a branch the remote deleted: it answers `not-found`, the edit leaves `jig writes`, and the
next edit takes a new name. An edit still waiting is never left out of sight: when an epic opened or
finished since it was made, or when it never reached the remote above edits that were turned down, the
next write is refused with `write-still-waits` until you merge, close or move it. The full shape is in
[the schema](https://github.com/fapost-lab/jig/blob/main/schemas/json.md).

### Changing a roadmap

Each item in `jig spec list --json` has an `id`, which a write names it by:

```bash
jig spec item add foo --phase 2 --text "Export a page" --revision 1793825280 --json
jig spec item move foo i-7d2bc8dc7707 --phase 1 --top --revision 1793825290 --json
jig spec item file foo i-7d2bc8dc7707 --task export-page --revision 1793825300 --json
jig spec item file foo i-7d2bc8dc7707 --new export-page --goal "Export a page" --revision 1793825300 --json
```

`add` takes `--after <item>`, `--top` or `--bottom`, the bottom by default, and `move` takes the same or
`--phase`. `file` names a task filed earlier with `jig task new`: the item gets the task in front, and the
task is linked to the spec. With `--new <task-id> [--goal <text>]` in
place of `--task`, `file` files the task as well, in the same write, so the `--revision` you carry is the one of
your read: `jig task new` moves the revision, and a task filed first would make the write stale. Everything is checked
before anything is written; a refusal files no task. A spec with an open epic is edited through a pull request into the epic.

The `id` holds through a move, a check and a filing, because it is a digest of the item's words. Reword the
item and the `id` changes, and a write with the old one is refused with `not-found`: it never touches
the wrong item. Read again.

### Deciding knowledge

```bash
jig knowledge accept feature-alpha --revision 1793825286 --json
jig knowledge reject feature-beta --revision 1793825290 --json
jig knowledge reviewed convention-stub --revision 1793825295 --json
```

```json
{"schema":1,"revision":1793825286,"generated_at":"2026-11-04T20:55:49Z","data":{"decisions":[{"id":"feature-alpha","decision":"accepted","path":".ai/knowledge/features/alpha.md"}],"write":{"target":"knowledge","branch":"knowledge/decisions","base":"main","commit":"d84d893f204caa70748ed0c58f9779be39197148","commits":1,"pushed":true,"pr":null,"merged":false,"committed":true,"level":"push","note":"agent.git is push: the pull request is yours"}}}
```

Without `--revision` and `--json` these commands do what they always did: they change the file in your
working tree, for a person deciding with an agent.

`reject` also drops the link of an accepted stub whose file changed, has no approved text recorded, or
is gone (`changed`, `unrecorded`, `missing` in `sources --json`): the stub becomes `rejected`, stays at
its path, and no agent is handed the file any more. A stub whose file is unchanged is refused
`not-proposed`.

A decision is judged on the branch it is written on, not on your checkout. A proposal committed only
here, or a file edited only here, is not there yet: the read says so with `decidable: false` and the
`reason` the write would be refused with, `not-on-base` or `not-on-branch`, so a page can say "push it
first" or "after the decisions waiting land" before anyone presses the button.

## Asking a running task to pause

A task an agent is working on cannot be paused from outside without losing the agent's step. Ask
instead, and the agent pauses the task when it finishes the stage it is on:

```bash
jig queue request booking-message pause --reason "Need to check the copy first" --revision 1792079790 --json
jig queue cancel booking-message pause --revision 1792079790 --json
```

The request is kept until it is honoured or cancelled, whatever stage the task reaches meanwhile. The
agent working on the task honours it at its next stage — an autopilot run when it enters the stage,
any agent when the stage reads its context with `jig context resolve --task <id> --stage <stage>`:
the task becomes paused, the request goes, and the agent stops. `jig task pause` honours it too.

The answer is the request as the queue now holds it, `null` after a cancel:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"ref":"task:booking-message","request":{"kind":"pause","requested_at":"2026-10-19T12:00:00Z","reason":"Need to check the copy first"}}}
```

While it waits, `jig task list --json` shows it on the task as `pause_request`, with
`requested_at` for the age you show beside it, and offers `cancel-pause-request` instead of
`request-pause`. Asking twice is refused with `already-exists`, and the first request keeps its time.
Asking a task that is already paused, or finished, is refused.

## Resuming a paused task

A paused task offers `resume`. Send it with the revision you read:

```bash
jig task resume booking-message --revision 1792079790 --json
```

A pause an agent made for a request puts nothing aside, so the resume only clears the pause and runs
in any checkout — your program may run it in the clone's main checkout even when the task works in
a worktree of its own. A pause a person made with `--stash` put their uncommitted work aside; that
resume applies it, so it must run where the task's branch is checked out, and from anywhere else it
is refused with `wrong-checkout`.

The answer is the task as `jig task list --json` lists it, now with `"paused":false`, and what the
resume found:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"task":{"id":"booking-message","paused":false,"…":"…"},"resume":{"paused_days":2,"stash":null,"uncommitted":0,"overlap":["src/booking/message.ts"]}}}
```

`overlap` lists the files the task changed that also changed on its base while it was paused — worth
showing before the person continues. A resume somebody else made first is refused with
`not-paused`; any other write in the clone since your read, with `stale-revision`.

## Closing a task

A task offering `close` is closed with the revision you read, once the person has said yes:

```bash
jig task set booking-message status consolidated --revision 1792079790 --json
```

The answer is the task as `jig task list --json` lists it, now with `"status":"consolidated"`:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"task":{"id":"booking-message","status":"consolidated","…":"…"}}}
```

The command asks the forge about the pull request now, so it can refuse a close the page offered
from a stale cache. A close that is not offered — the knowledge decision is not recorded, or the pull
request is not merged — is refused with `not-closable`, and its `message` is the reason to show as
it is, the one the `close` action carries. A write somebody else made since your read is refused with
`stale-revision`, an unknown task with `not-found`; nothing is written in any of them.
`--revision` and `--json` belong to this close alone: `jig task set booking-message class T2
--revision 1792079790` is refused with `usage`, not written without the check.

## Filing a task

A program files a task with `jig task new`, giving the goal on the command line instead of writing
a file first:

```bash
jig task new booking-message --goal "Guests get a confirmation message after booking" --json
```

The goal becomes the paragraph under `## Goal` in the task's `task.md`. It is one line of text, not
empty and not starting with `#`. Without `--goal` the task has none yet, and its `goal` is `null`.
You may add `--class` and `--domains` as a person would. The answer is the filed task, the same
object `jig task list --json` lists for it:

```json
{"schema":1,"revision":1792405174,"generated_at":"2026-10-19T10:22:28Z","data":{"task":{"id":"booking-message","class":null,"status":"active","issue":null,"goal":"Guests get a confirmation message after booking","knowledge_consolidated":false,"paused":false,"pause_request":null,"created_at":"2026-10-19","updated_at":"2026-10-19","branch":null,"base_branch":"main","worktree":null,"gate":null,"autopilot":null,"pull_request":null,"housekeeping_flags":[],"actions":[...]}}}
```

When the id is taken, the refusal says so in its own code, so your program can ask the person for
another id rather than show a generic failure:

```json
{"schema":1,"revision":1792405176,"generated_at":"2026-10-19T10:22:28Z","error":{"code":"already-exists","message":"task new: task already exists: booking-message"}}
```

An id Jig does not accept — a space, a leading dash — and a goal that is empty or spans lines are
`usage`.

The full field list is in the repository, in
[`schemas/json.md`](https://github.com/fapost-lab/jig/blob/main/schemas/json.md).

## A task's documents

A task keeps its documents — `task.md`, the analysis, the design, the plan, the review and the
rest — in its workspace. When the task runs in a worktree, only Jig knows where that workspace really
is, so a program asks Jig instead of looking for the files:

```bash
jig task artifacts booking-message --json
```

The answer lists every kind of document Jig knows, always all twelve and always in the same order,
so a page can show a fixed set and mark what is not written yet:

```json
{"schema":1,"revision":1792405174,"generated_at":"2026-10-29T10:22:28Z","data":{"task":"booking-message","artifacts":[{"kind":"task","state":"present","reason":null,"updated_at":"2026-10-29T09:12:40Z","bytes":1365},{"kind":"discovery","state":"missing","reason":null,"updated_at":null,"bytes":null},...]}}
```

`state` is `present`, `empty` (the file is there with nothing in it), `missing` (not written yet) or
`unavailable` (there is something Jig will not read — a link out of the workspace, a directory — and
`reason` says what). `updated_at` and `bytes` are the file's, for `present` and `empty`.

Open one of them with:

```bash
jig task artifact read booking-message plan --json
```

```json
{"schema":1,"revision":1792405174,"generated_at":"2026-10-29T10:22:30Z","data":{"task":"booking-message","kind":"plan","updated_at":"2026-10-29T09:12:40Z","bytes":2221,"content":"# Plan\n\n..."}}
```

`content` is the Markdown exactly as it is in the file. A document not written yet is refused as
`not-found`, and so is a task the clone does not have. Both commands only read: the `revision` stays
where it was, and comparing it tells you when to read again. Without `--json`, `jig task artifact
read` prints the document itself.

## Knowledge waiting for a person

Documents an agent proposed wait for a person to accept or reject them, and a linked source file
that changed since it was approved waits for a person to approve the new text. Both are readable as
data, so a page can show them without parsing text:

```bash
jig knowledge proposed --json
jig knowledge sources --json
jig knowledge sources --diff convention-coding-style --json
jig knowledge read convention-coding-style --json
```

`proposed` lists each document whose status is `proposed`, with its `id`, `type`, `domains`, its
`path` and `paths`, its `summary` and, for a stub that links an existing file, that file as `source`
(`null` for the rest):

```json
{"schema":1,"revision":1793805159,"generated_at":"2026-11-04T15:12:41Z","data":{"proposals":[{"id":"feature-billing","type":"feature","domains":["billing"],"path":".ai/knowledge/features/billing.md","paths":["src/billing/**"],"summary":"How invoices are issued","source":null,"waiting":null},{"id":"convention-release","type":"convention","domains":["core"],"path":".ai/knowledge/sources/release.md","paths":[],"summary":null,"source":"docs/release.md","waiting":null}],"waiting":null}}
```

`sources` lists each stub with the `state` of the file it links: `ok`, `changed` (the file is not
the text that was approved), `unrecorded` (nothing was ever approved), `missing`, or the stub's own
status while it is not accepted yet, with the file's size in `bytes` and the counts the text form
prints on its last line:

```json
{"schema":1,"revision":1793805159,"generated_at":"2026-11-04T15:12:49Z","data":{"sources":[{"id":"convention-coding-style","state":"changed","status":"active","path":".ai/knowledge/sources/coding-style.md","source":"docs/coding-style.md","bytes":62,"waiting":null},{"id":"convention-release","state":"proposed","status":"proposed","path":".ai/knowledge/sources/release.md","source":"docs/release.md","bytes":21,"waiting":null}],"counts":{"linked":2,"changed":1,"unrecorded":0,"missing":0},"waiting":null}}
```

`sources --diff <id>` answers for one stub and carries the difference between the approved text and
the file now in `diff`, a unified diff in one string:

```json
{"schema":1,"revision":1793805159,"generated_at":"2026-11-04T15:12:50Z","data":{"id":"convention-coding-style","source":"docs/coding-style.md","state":"changed","approved_hash":"d9dc8059e3a61983d9e3ab6d32dfabc8aa7feb2d","diff":"--- docs/coding-style.md (approved)\n+++ docs/coding-style.md\n@@ -1,2 +1,4 @@\n # Style\n Use tabs.\n+Use spaces, never tabs.\n+Quote \"everything\".\n","lossy":false}}
```

`diff` is `null` when there is nothing to compare: the file is `ok` or `missing`, was never approved
(`unrecorded`), or is `changed` but git no longer has the approved text. In the last two cases the
file is read whole. A source can hold anything, quotes and control characters
included; the answer stays one valid JSON line. Bytes that are not UTF-8 are dropped from `diff`, and
`lossy` says so. An id no document has, or a document that links no source, is refused as
`not-found`. These reads write nothing: the `revision` stays where it was.

`read <id>` gives the text being decided: the document's whole file, frontmatter included, whatever its
status, and for a stub the file it links as it is now (`source` is `null` for any other document, and
for a stub whose file is missing). Bytes that are not UTF-8 are dropped from a text and its `lossy` says
so. An id no document has is refused as `not-found`. It has no text form.

```json
{"schema":1,"revision":1793805159,"generated_at":"2026-11-04T15:12:51Z","data":{"id":"convention-release","status":"proposed","path":".ai/knowledge/sources/release.md","bytes":261,"content":"---\nid: convention-release\n...","lossy":false,"source":{"path":"docs/release.md","bytes":21,"content":"# Release\n...","lossy":false}}}
```

A decision is [written on a branch of its own](#deciding-knowledge). Until it lands the document here
still reads `proposed` or `changed`, and its `waiting` says what was decided and where:
`{"decision":"accepted","branch":"knowledge/decisions","pr":"https://…"}`, `null` when nothing waits.
The `waiting` beside the list is the write itself. Each proposal and each source also carries
`decidable` and `reason`: `true` and `null` when a decision sent now would be judged on what the read
shows, as of the last fetch; otherwise `false` and `not-on-base` or `not-on-branch`, the code the
decision would be refused with.

## Upgrading a project

A program upgrades a project the way a person does, and reads what happened:

```bash
jig upgrade --json
```

The text the command prints for a person goes to stderr; stdout holds the envelope. `outcome` says
how it ended — `upgraded`, `staged` (left for the person to commit), `nothing-to-do`, `incomplete` (run
it again) — and `git` how far it went by the project's `agent.git`: the branch, the commit, the pull
request and whether it was merged. `manual_steps` lists what this release asks for by hand; an agent
can do those, a script cannot. `jig upgrade --dry-run --json` changes nothing and lists in
`would_stop` what a real run would refuse for. Which projects need an upgrade at all is the
`upgrade-available` item of `jig status --json` ([What needs you](#what-needs-you)).

An upgrade at `agent.git: pr` ends with its pull request open and the project back on its base
branch, still at the old Jig. `jig status --json` keeps saying so — `upgrade-pull-request-waiting`,
then `upgrade-pull-request-merged` — so a program shows the state from the project, not from its
own memory. Once it is merged, the program brings it in:

```bash
jig upgrade --land --json
```

It asks the forge, checks the base branch out, fast-forwards it to origin's and deletes the upgrade's
branch. Its data has the shape of `jig upgrade --json` with `outcome` `landed` or `nothing-to-do`
and a `land` object beside `git`. A pull request still open is refused as `not-merged`; uncommitted
changes, a checkout on another branch or a base that cannot be fast-forwarded as `upgrade-blocked`.
Neither changes anything.

When the upgrade cannot start, it changes nothing and says why in its own code, with every reason in
the message:

```json
{"schema":1,"revision":1792500000,"generated_at":"2026-10-25T09:08:11Z","error":{"code":"upgrade-blocked","message":"upgrade: nothing was changed:\n  - the working tree has uncommitted changes; commit them, stash them (`git stash`), or finish the task they belong to, then run `jig upgrade` again"}}
```

The whole shape is in `schemas/json.md`.

## Your settings

A page can show the settings of a project and change the person's own. `jig config keys --json`
lists every key Jig reads, with the value this clone gets for it and where that value comes from:

```bash
jig config keys --json
```

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-11-04T12:00:00Z","data":{"keys":[{"key":"agent.git","value":"none","set":false,"source":"default","scope":"local only","kind":"choice","allowed":["none","commit","push","pr","merge"],"default":"none","description":"How far your agent takes a finished task with git.","secret":false}]}}
```

`source` is `local` (the person's `.ai/config.local.yaml`), `project` (the team's `.ai/config.yaml`)
or `default`. `scope` says who may answer the key: `project` keys are the team's and a page shows
them read-only; `local` and `local only` keys the person may set. `kind` tells the page which
control to offer: a checkbox for `boolean`, a choice among `allowed` for `choice`, a field for the
rest (`duration`, `number`, `text`, `list`). A value is always a string, as the file writes it.

<Warning>
  A secret's value never leaves Jig in a `--json` answer. `notify.telegram.token` has `"secret":true`
  and `"value":null` always; `set` says only whether a token is there. Jig also refuses to take a
  token on a command line, so a page cannot set it either: the person writes it into the file, or
  runs `jig notify setup` in their own terminal.
</Warning>

The person's own settings are changed with the commands a person uses, adding `--json`:

```bash
jig config set agent.git pr --local --json
jig config unset agent.git --local --json
```

A write answers with the new state of each key it touched, as `keys` lists it, and `unset` also
names in `removed` the keys it took out of the file. A key that cannot be written, or a value it
does not accept, is refused with `unknown-key`, `not-local`, `invalid-value` or `secret-key`
([Why a command refused](#why-a-command-refused)), and nothing is written. Both commands take
`--revision <n>` like a queue write: another write in the project since your read is refused with
`stale-revision`, so a page and `jig-setup` writing the same file cannot overwrite each other's
change unseen. `.ai/config.yaml` is the team's; no command here writes it.
