---
title: "Reading Jig as data"
description: "Read your project's tasks, specs and what needs you from a script, a bot or a dashboard as JSON, without parsing text and without touching the network."
---

Jig's commands print text for a person. A program — a CI step, a chat bot, a dashboard such as
[Jig UI](https://jig-ui.fapost.in) — can ask for the same answer as JSON instead, by adding
`--json`. Today `jig task list`, `jig spec list`, `jig status`, `jig queue list` and `jig queue next` offer it, and
`jig queue` and `jig task new` answer in it when they write; more commands will, in the same form.

```bash
jig task list --json
jig task list --json --all
jig spec list --json
jig status --json
jig queue list --json
```

<Info>
  A `--json` read never touches the network. It reads files on your disk and asks Git about your
  local repository; it never calls `gh` or fetches. You can run it as often as you like, in many
  projects at once, without running into a forge's rate limits.
</Info>

## The envelope

Every `--json` command prints exactly **one line**: a JSON object called the envelope. On success
it carries the answer in `data`:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-15T12:00:00Z","data":{"tasks":[...],"hidden":0,"housekeeping":null}}
```

When the command refuses — an unknown flag, a project without Jig — it still prints one line, with
`error` in place of `data`, and exits with a non-zero status:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-15T12:00:00Z","error":{"code":"usage","message":"task list: invalid status: bogus"}}
```

- `schema` is `1`. It changes only when a field is removed, renamed or changes type. New fields
  can appear at any time without it changing, so ignore the fields you do not know.
- `revision` is a number that changes whenever Jig writes anything in the project — a task, its
  documents, a spec, knowledge, a housekeeping run — in this checkout or any of its worktrees. If it
  is the same as on your last read, Jig changed nothing; if it differs, read again. It is `0` before
  Jig's first write, and only its changes mean anything: compare it, do not do arithmetic with it.
  A file changed by hand or by git — your `git pull`, or the branch Jig checks out after a merge —
  does not change it: watch the files too if that matters to you.
- `generated_at` is when the read started, in UTC.
- `error.code` says why the command refused, in a word your program can act on (below).
  `error.message` is the same text the command prints after `jig: error:`, meant for a person.

Warnings meant for a person still go to stderr, so stdout always holds just the envelope.

### Why a command refused

Act on `error.code`, never on the wording of `error.message`: codes stay as they are, messages may
be reworded.

| `error.code` | What happened |
|---|---|
| `usage` | the command was called with an argument it does not take, or with a value it does not accept — check how your program calls it |
| `not-a-repository` | it ran outside a Git repository |
| `not-initialised` | the repository has no Jig yet; `jig init` sets it up |
| `stale-revision` | a write carried a `revision` that is no longer current: something changed since your program read it. Nothing was written — read again, and show the person the conflict |
| `not-found` | the task or epic named does not exist, or is not in the queue where the command needs it |
| `already-exists` | what the command would create is already there: a task with that id. Nothing was written — pick another id |
| `failed` | anything else: the message says what |

New codes may appear, for refusals that today read `failed`. Treat a code you do not know as
`failed`. Whatever the code, the command exits with a non-zero status.

## Tasks

`jig task list --json` lists the same tasks as `jig task list` with the same flags: unfinished ones
by default, everything with `--all`, one status with `--status <status>`. `data.hidden` says how many
finished tasks were left out.

Each task carries what Jig knows about it:

```json
{
  "id": "booking-message",
  "class": "T1",
  "status": "active",
  "issue": null,
  "goal": "Show the booking reference in the confirmation message.",
  "knowledge_consolidated": false,
  "paused": false,
  "created_at": "2026-10-14",
  "updated_at": "2026-10-15",
  "branch": "task/booking-message",
  "base_branch": "main",
  "worktree": {"path": "/home/me/shop.worktrees/booking-message", "uncommitted": 2},
  "gate": null,
  "autopilot": null,
  "pull_request": {
    "url": "https://github.com/me/shop/pull/42",
    "state": "open",
    "ci": "green",
    "fetched_at": "2026-10-15T09:00:00Z"
  },
  "housekeeping_flags": [],
  "actions": [
    {"id": "start", "command": "jig task start booking-message", "offered": false, "reason": "task start: already started on task/booking-message; ..."},
    {"id": "pause", "command": "jig task pause booking-message", "offered": true, "reason": null},
    ...
  ]
}
```

A fact Jig does not have is `null`: `branch` is `null` for a task not started yet, `goal` for a task
whose `## Goal` holds nothing but an HTML comment such as the template's `<!-- … -->` hint, `gate`
for a task without a design approval step, `autopilot` for a task that never ran on autopilot. The
flags are the ones the last `jig housekeeping` run raised and that still apply, for example
`needs-consolidation` for merged work nobody has closed yet; `data.housekeeping` says when that run
was.

`pull_request` says whether the pull request is `open`, `merged` or `closed`, and how its checks
went: `green`, `red`, `pending`, or `none` when no check ran. Both are what the last `jig
housekeeping` heard from the forge, at `fetched_at`; the read itself never asks. When housekeeping
has not run, or the forge did not answer, they are `null` or as old as `fetched_at` says — run
`jig housekeeping` to refresh them. Checks are asked only for open pull requests, and GitLab's list
carries none, so there `ci` is `null`.

## What a person may do next

`actions` lists what a person can do with the task right now, so a dashboard can show the right
buttons without knowing Jig's rules. Every task carries the same twelve actions, in the same order:

| `id` | What it does |
|---|---|
| `start` | Start a task that was filed for later |
| `pause`, `resume` | Set the task aside, and pick it up again |
| `request-pause`, `cancel-pause-request` | Ask a running task to pause when it finishes its current stage, and take the request back |
| `approve-gate` | Approve the design of a T3 or T4 task waiting at its gate |
| `answer-stop` | Answer an autopilot run that stopped to ask you something |
| `set-class` | Change the task's class |
| `ship` | Commit, push and open the pull request, as far as your settings let the agent |
| `close` | Close a task whose work has landed |
| `abandon` | Give the task up |
| `reopen` | Take back an abandoned task |

`offered` is `true` when Jig would accept the action now, and `command` is the Jig command that does
it, with the values you supply written as `<text>`, `<Tn>` or `<file>`. When `offered` is `false`,
`reason` says why, in the same words the command itself would refuse with.

Jig judges the task's own state. A few things it cannot know until the command runs: whether you are
in the right place (run `resume` and `ship` in the task's worktree when it has one), whether there is
anything to commit, and whether the forge agrees. `close` trusts what the last `jig housekeeping`
heard about the pull request: until it has seen the merge, `close` stays unavailable.

More actions may appear later; ignore the ones you do not know.

## Specs

`jig spec list --json` lists the same specs as `jig spec list`, each with its roadmap as data: its
phases, the items of each phase, and how far it has come.

```json
{
  "id": "booking",
  "title": "Booking flow",
  "missing_files": [],
  "release": "minor",
  "epic": {"branch": "epic/booking", "state": "open", "checked_out": false, "missing": false, "ref": "refs/remotes/origin/epic/booking"},
  "progress": {"done": 1, "total": 3, "filed": 1, "fog": 1},
  "phases": [
    {
      "phase": 1,
      "title": "Book a table",
      "done": 1, "total": 3, "filed": 1, "fog": 1,
      "items": [
        {"text": "`booking-form` — the form", "checked": true, "task": "booking-form", "fog": false},
        {"text": "`booking-message` — the confirmation", "checked": false, "task": "booking-message", "fog": false},
        {"text": "fog: reminders by text message", "checked": false, "task": null, "fog": true}
      ]
    }
  ]
}
```

`progress` is the same count `jig spec list` prints, and the sum of the phases. Each item says
whether it is checked, which task it names, if any, and whether it is still fog.

A spec built on an epic branch keeps its roadmap there. When you read it from another branch, the
phases come from the epic's branch as your repository last fetched it — `epic.ref` names it — and
when that branch is nowhere on your disk, `epic.missing` is `true` and `progress` is `null`.
`release` is the version level the epic will be released at, or `null` when none was recorded.

## What needs you

`jig status --json` lists what needs a person in the project — the same items, in the same order,
as the "Needs you" cards on the status page (`jig status --open`), because both are built from one
list. An empty `attention` means nothing needs you.

```json
{
  "attention": [
    {
      "kind": "autopilot-stopped",
      "subject": {"type": "task", "id": "booking-message"},
      "tasks": ["booking-message"],
      "title": "Autopilot stopped and is waiting for you",
      "detail": "stopped 5 min ago: Which payment provider should the refund use?",
      "todo": "Answer the agent in this task's session; it resumes the run.",
      "url": null
    }
  ],
  "housekeeping": {"ran_at": "2026-10-15T09:00:00Z", "forge": "github", "stale": false},
  "knowledge_counts_at": "2026-10-15T08:00:00Z"
}
```

A program acts on `kind` and `subject`; `title`, `detail` and `todo` are the words the page shows a
person, and may be reworded. The kinds cover a stopped autopilot run (`autopilot-stopped`, or
`phase-stopped` for a phase run, whose `tasks` lists every stopped task), a design at its gate
(`gate-waiting`, `gate-changed`), a finished task waiting for your git step (`git-step`), pull
requests to review, merge or close (`pull-request-waiting`, `pull-request-was-open`,
`pull-request-of-abandoned-task`), what housekeeping flagged (`needs-consolidation`, `wrong-base`,
`closed-unmerged`, `worktree-kept`), knowledge to decide (`knowledge-proposed`, `sources-changed`)
a newer jig (`release-available`), and a project whose own Jig is older than the one on your machine
(`upgrade-available` — the item a program lists to show which projects need `jig upgrade`; it alone
carries `"versions": {"from": "0.32.0", "to": "0.33.0"}`, the project's Jig and your machine's).

Pull request items are as old as the last `jig housekeeping` run; `housekeeping.stale` is `true`
when that run is older than your housekeeping cadence or the forge did not answer, so one may be
missing. The knowledge counts are the ones the last full `jig status` took for the page, at
`knowledge_counts_at`.

## The queue

The queue holds the priority, order and dependencies of tasks and epics, one per project, shared
by every worktree. `jig queue list --json` (or `jig queue --json`) reads all of it:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"items":[
  {"ref":"epic:booking","kind":"epic","id":"booking","level":null,"position":100,"priority":0,"depends_on":[]},
  {"ref":"task:booking-form","kind":"task","id":"booking-form","level":"epic:booking","position":100,"priority":null,"depends_on":[]},
  {"ref":"task:booking-message","kind":"task","id":"booking-message","level":"epic:booking","position":200,"priority":1,"depends_on":[{"on":"task:booking-form","reason":"Quotes the form"}]}
]}}
```

`items` is in the queue's order: the top level (`level` `null`) by `position`, then each epic's
tasks under their `level`. An empty queue is `"items":[]`. An item is the same object a write
below answers with, so a board renders both with one piece of code.

The queue holds order, not the tasks themselves: read it together with `jig task list --json`
and join a `task` item to a task by `id`, and an `epic` item to `jig spec list --json` by the
spec's `id`. All of them carry the same `revision` when nothing was written between the reads, and
the one you send with a change is the `revision` of the queue read you showed. An item whose task
is finished, or gone, stays in the queue until it is removed; it has no match in the default task
list, so join against `jig task list --json --all` or show it as it is.

### Which task is next

`jig queue next --json` answers what the queue advises, so a board needs no rules of its own. It
reads the queue, the tasks' state and the last `jig housekeeping` run, never the network, and
changes nothing:

```json
{"schema":1,"revision":1792693064,"generated_at":"2026-10-22T18:17:22Z","data":{"next":{"ref":"task:booking-form","kind":"task","id":"booking-form","level":null,"position":100,"priority":1,"started":true},"reason":null,"waiting":[{"ref":"task:booking-message","on":"task:booking-form","state":"unknown","reason":"The message quotes the form"}],"not_queued":1}}
```

`next` is the task to take, or `null` with a `reason` (`waiting`, `paused` or `empty`) when there
is none. `waiting` lists each dependency that holds a candidate back, in `state` `open`, `broken`
(it never ends; drop it with `jig queue undepend`) or `unknown`. `not_queued` counts the active
tasks outside the queue. The fields are in [the schema](https://github.com/fapost-lab/jig/blob/main/schemas/json.md).

## Changing the queue

A program changes the queue with the same commands a person uses, adding `--json` and the
`revision` of the read it decided on:

```bash
jig queue move booking-message --after booking-form --revision 1792079790 --json
jig queue set booking-message --priority 0 --revision 1792079790 --json
jig queue depend booking-message --on booking-form --reason "Quotes the form" --revision 1792079790 --json
```

If anything changed in the project since that read — another person's drag, an agent's task
update — the write is refused with `stale-revision` and nothing is written: read again and let the
person decide again. Two programs that send the same revision cannot both land: at most one does,
and when a third write slips in between, neither.
A write that lands answers with the item as the queue now holds it:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"ref":"task:booking-message","item":{"ref":"task:booking-message","kind":"task","id":"booking-message","level":null,"position":150,"priority":0,"depends_on":[]}}}
```

The envelope's `revision` is taken before the write, so with `--revision` it is the one you sent;
the write raised it, so read again before the next change. A move moves one item, never the others: drag an item by sending one
`move`, not by renumbering the list. `position` is only for comparing within a `level` — the top
level (`null`) orders epics and tasks without an epic, and `epic:<spec-id>` orders that epic's tasks.

## Asking a running task to pause

A task an agent is working on cannot be paused from outside without losing the agent's step. Ask
instead, and the agent pauses the task when it finishes the stage it is on:

```bash
jig queue request booking-message pause --reason "Need to check the copy first" --revision 1792079790 --json
jig queue cancel booking-message pause --revision 1792079790 --json
```

The request is kept until it is honoured or cancelled, whatever stage the task reaches meanwhile. The
agent working on the task honours it at its next stage — an autopilot run when it enters the stage,
any agent when the stage reads its context with `jig context resolve --task <id> --stage <stage>`:
the task becomes paused, the request goes, and the agent stops. `jig task pause` honours it too.

The answer is the request as the queue now holds it, `null` after a cancel:

```json
{"schema":1,"revision":1792079790,"generated_at":"2026-10-19T12:00:00Z","data":{"ref":"task:booking-message","request":{"kind":"pause","requested_at":"2026-10-19T12:00:00Z","reason":"Need to check the copy first"}}}
```

While it waits, `jig task list --json` shows it on the task as `pause_request`, with
`requested_at` for the age you show beside it, and offers `cancel-pause-request` instead of
`request-pause`. Asking twice is refused with `already-exists`, and the first request keeps its time.
Asking a task that is already paused, or finished, is refused.

## Filing a task

A program files a task with `jig task new`, giving the goal on the command line instead of writing
a file first:

```bash
jig task new booking-message --goal "Guests get a confirmation message after booking" --json
```

The goal becomes the paragraph under `## Goal` in the task's `task.md`. It is one line of text, not
empty and not starting with `#`. Without `--goal` the task has none yet, and its `goal` is `null`.
You may add `--class` and `--domains` as a person would. The answer is the filed task, the same
object `jig task list --json` lists for it:

```json
{"schema":1,"revision":1792405174,"generated_at":"2026-10-19T10:22:28Z","data":{"task":{"id":"booking-message","class":null,"status":"active","issue":null,"goal":"Guests get a confirmation message after booking","knowledge_consolidated":false,"paused":false,"pause_request":null,"created_at":"2026-10-19","updated_at":"2026-10-19","branch":null,"base_branch":"main","worktree":null,"gate":null,"autopilot":null,"pull_request":null,"housekeeping_flags":[],"actions":[...]}}}
```

When the id is taken, the refusal says so in its own code, so your program can ask the person for
another id rather than show a generic failure:

```json
{"schema":1,"revision":1792405176,"generated_at":"2026-10-19T10:22:28Z","error":{"code":"already-exists","message":"task new: task already exists: booking-message"}}
```

An id Jig does not accept — a space, a leading dash — and a goal that is empty or spans lines are
`usage`.

The full field list is in the repository, in
[`schemas/json.md`](https://github.com/fapost-lab/jig/blob/main/schemas/json.md).
