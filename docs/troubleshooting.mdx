## Not sure what went wrong?

Copy the error message into your AI chat and say:

```text Send to your agent
Help me fix this before continuing the task.
Explain what happened, what you need from me, and how we will check the fix.
```

<Tip>
  Include what you were trying to do and the last command or action. Remove passwords, API keys,
  and other private values before sharing an error message.
</Tip>

Start with `jig doctor`. It checks the machine, the project and your agent's instructions, one line
each, and prints a fix for every warning. On Windows, run it in Git Bash, or as
`.ai\scripts\jig.cmd doctor` in PowerShell.

If the trouble turns out to be Jig itself rather than your project, see [Known issues](/known-issues)
— the faults we know about, and what to do instead of each.

## The agent does not follow Jig

| Symptom | What to do |
|---|---|
| The agent works without classifying the task or creating one | Your `AGENTS.md` or `CLAUDE.md` probably lacks the Jig section — `jig status` shows `instructions (...): no Jig section`. Ask the agent to *"connect Jig to my AGENTS.md"*, or add the section by hand ([Install](/install#2-set-up-a-project)). For a single request, name the skill: `/jig-task` in Claude Code, `$jig-task` in Codex. |
| Jig's own instructions never seem to improve | Your `AGENTS.md` probably carries the Jig section without its markers — `jig status` shows `instructions (...): Jig section in AGENTS.md is not marked`. `jig upgrade` reports it as `keep-unmarked AGENTS.md` and changes nothing. Ask the agent to *"connect Jig to my AGENTS.md"* and keep the `<!-- jig:begin -->` / `<!-- jig:end -->` lines it adds. |
| `jig upgrade` says `keep-modified AGENTS.md (Jig section)` | Someone edited inside the markers, so Jig keeps your text and stops updating that section — by design. To go back to the maintained version, replace the region between the markers with the one in `.ai/templates/AGENTS.md`. |
| The skills are missing in the runtime | Check that the runtime is listed under `adapters` in `.ai/config.yaml`, run `jig upgrade`, and reopen the agent session. |
| The agent does not know a rule your team wrote down | The document may still be proposed — `jig status` shows the count on its `proposals:` line. Ask the agent to *"review the proposals"*. |

## Installation

| Symptom | What to do |
|---|---|
| `jig: command not found` | Open a new terminal — the installer's `PATH` change reaches only new ones. Otherwise check that `~/.local/bin` (or, on Windows, the Jig `scripts` folder) is on `PATH`. |
| Something does not work on Windows | Run `jig doctor` and follow each `fix:` line; the installer's log is `%LOCALAPPDATA%\jig\install.log`. |
| `self-update` refuses | Commit or stash the changes in the Jig checkout. A developer checkout on a branch without an upstream is updated with Git directly. |
| `framework versions: ... global=unavailable` | There is no Jig on `PATH`, or it is not a full checkout. Harmless in CI; install it where you update from. |

## Projects and tasks

| Symptom | What to do |
|---|---|
| `not inside a git repository` | Change into the project, or make the folder a Git repository first. |
| `project is not initialised` | Run `jig init` in that repository. |
| `the repository has no commits yet` when starting a task | Commit what `jig init` added, then start again. |
| Starting a task refuses because of uncommitted changes | They belong to other work. Pause the task that owns them (*"pause it and stash the changes"*), or start the new one in a separate worktree. |
| `--worktree needs a directory link` | The disk supports neither symbolic links nor NTFS junctions (a network or FAT drive). Keep the project on a local disk, or start the task in the current checkout. |
| Filing a task refuses: this worktree keeps a `tasks/` folder of its own | A worktree started by Jig shares the project's task list, so a task filed inside it lands with all the others. A worktree you made yourself with `git worktree add` does not, and neither does one in a project whose ignore rule ends in `.ai/workspace/tasks/` — a task filed there would be invisible to the project and would go when the worktree went. The message names the checkout to file it in. |
| Several tasks match the branch | Tell the agent which one to continue. |
| `wrong-base` in the housekeeping report | A task's pull request was merged into a branch other than its base. It is kept; check where the work went. |
| Tasks that are merged but not closed | Say *"close what's merged"*; the agent asks you about each one. |
| The status page does not change | Look at the time at its top. If it is recent, nothing changed. If it is old, you may have an older copy open — open it again with `jig status --open`; in Firefox, automatic reloading can be turned off by the setting `accessibility.blockautorefresh`. |
| The status page says pull request data is *stale* | Run `jig housekeeping`; it asks GitHub or GitLab again. |

## Verification and upgrades

| Symptom | What to do |
|---|---|
| Verification reports skips | The project's tools are missing — install its dependencies (`npm install`, `composer install`, a virtual environment …) and run it again. A skip is not a pass. |
| Verification says **nothing was checked, so this is not a pass**, and exits 3 | A profile for your stack is active but none of its checks could run — its tools are missing. Install them (`npm install`, `composer install`, a virtual environment, `shellcheck` …) and run it again; `jig verify --list` shows which profiles are installed. Until then `jig task ship` will not ship, because there is no evidence to ship on and something can be done about it. |
| Verification says **nothing here checks this project**, and exits 0 | No profile covers this project, so there is nothing to install and nothing to wait for. Jig does not stop you — but nothing verified this change, and `jig task ship` says so again as it ships. If your stack has a profile, activate it in `.ai/config.yaml`; if it has none, the checks are yours to add. |
| Verification reports **incomplete**, and exits 3 | The run was killed rather than failing — usually because the machine ran out of memory or was overloaded. It is neither a pass nor a failure: run it again. If it keeps happening, run fewer things at once, or narrow the run. |
| Verification says it is **waiting for another run** | Another `jig verify` is already going in this clone — in this checkout or in one of its worktrees — and running both makes both slower. It goes ahead as soon as the other finishes, and says how long it waited. To never wait, set `verify.busy_ttl: 0` in `.ai/config.local.yaml`. |
| Verification refuses: framework files pending | Run `jig upgrade --dry-run`, then `jig upgrade`, review the change, and verify again. |
| A map line fails a profile | The error names the file and line in `.ai/verify/<profile>.map`; each line needs a pattern and a decision ([Configuration](/configuration#a-verification-map-for-your-project)). |
| `upgrade` kept some files | You edited them; the report marks them `keep-modified` or `keep-conflict`. Compare with the new version and reconcile by hand. A file marked `already-placed` needs nothing from you: it already holds this version's bytes, and the run has just recorded that. |
| `jig status` reports **drift** on framework files right after an upgrade | The upgrade was carried out by the version being replaced, which recorded the hashes the way it computed them. Run `jig upgrade` once more: the new code recognises the files as already placed, records them, and the drift goes. Nothing is wrong with the files themselves. |
| `upgrade` says **N item(s) still not installed** | The run asked the install it had just made, and something is missing — usually because the upgrade was carried out by the older version, which did not know about every file the new one ships. Run `jig upgrade` again; the second run is done by the new code and finishes the job. |
| `upgrade` cannot determine the framework source | Pass `--from /absolute/path/to/jig`; an installed copy is not the full source. |
| `upgrade` says `manifest unchanged` | It placed nothing, so the project stays on the checkout it was installed from. To move it onto the one you passed, run `jig init --from <dir>` (add `--link` in link mode). |
