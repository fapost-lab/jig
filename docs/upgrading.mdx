You install Jig once and upgrade it many times. [Install](/install#keep-jig-up-to-date) covers the
two commands; this page is about what happens afterwards — what the upgrade did on its own, what it
left for you, and why the line between them is where it is.

```bash
jig self-update          # the tool on your machine
jig upgrade --dry-run    # in a project: what would change
jig upgrade              # in a project: update its copy of Jig
```

`jig doctor` tells you when it is worth running the first of these: its `latest release` line asks
the tool's own origin for the newest published tag and reports one of three things — a newer release
is out (with the two commands above as the fix), this is already the newest, or it could not check
(no network, or nothing to ask) rather than guessing "up to date" from silence.

You do not have to remember to run `jig doctor` for this. Housekeeping asks the same question once
a day (`housekeeping.cadence`) as part of its own fetch, and `jig status` — plain text or
`--html`/`--open` — shows a newer release the moment one is out, with the same two commands as the
fix. It says nothing when there is nothing to say: no check yet, the last one could not reach the
origin, or this is already the newest.

## What the upgrade does, and what it leaves alone

`jig upgrade` copies from the Jig on your machine. It replaces the files Jig installed and you did
not edit, removes the ones Jig no longer ships unless you edited them, and keeps and reports
everything else — as one change of its own, on a branch of its own
([below](#an-upgrade-is-a-change-of-its-own)).

**The first upgrade from 0.15.0 or older ends with a shell error.** Once the run has done its work,
`.ai/scripts/jig` reports something like `line 133: cmd: unbound variable` — the wording and the
line number depend on the version you came from, and from versions before 0.15.0 the closing summary
may be missing as well. Nothing is broken: the files were already placed, and the message arrives
after them, from the old `jig` that replaced itself while it was still being read. One file may be
left unplaced — more in a project with clean filters — so run `jig upgrade` once more; the second
run places what is left and ends cleanly. Then
`jig version` reports the new version and `jig doctor` reports its upgrade check as `up to date`.

The exception is a project whose clean filters cover Jig's own scripts and that has upgraded
before. There the old copy replaces its entry point but not its libraries, and from then on every
`.ai/scripts/jig` command stops at once with `line 37: jig_clear_git_location_env: command not
found`. Upgrade that project with the `jig` on your machine instead, as
[From 0.16.0 to 0.16.1](#from-0160-to-0161) describes: it places the rest.
This happens on that first upgrade only: since 0.15.1 the upgrade writes each file beside its place
and renames it.

Three things it will not do, and none of them are oversights.

**It does not edit `.ai/config.yaml`.** That file belongs to your team, and nothing but a person
edits it. A key your file does not mention takes its default, so a config written for an older
version keeps working — which is also the trap, because that file is the only place anyone ever
sees which settings exist. So the upgrade *reports* the gap instead of closing it. At the end of a
real run (not a dry run) it prints a line like:

```text
.ai/config.yaml does not mention 2 key(s) this version reads, each on its default: worktree.carry, checkout.busy_ttl
hint: `jig config keys` lists them; that file is yours to change or leave as it is
```

That second line means what it says. Read the list, decide whether any of it is worth having, and
leave the file alone if none of it is. Nothing is wrong with a project that mentions no keys at
all.

**It does not install your project's tools.** Jig runs your checks; it does not provide them. If a
verification profile for your stack is active and its tools are missing, that is yours to fix with
`npm install`, `composer install`, a virtual environment, or whatever your project uses.

**It does not claim a region of a file your project already had.** Jig keeps the section between
`<!-- jig:begin -->` and `<!-- jig:end -->` in your `AGENTS.md` current — but only for a project
whose manifest records that Jig may. That record is written by `jig init`, on markers you agreed
to, and the first time Jig takes over part of a file you wrote is a moment that belongs to you
rather than to a command that ran while you were making coffee.

## An upgrade is a change of its own

From the next release on, `jig upgrade` does its work as one separate change, the way a task does:

1. **The newest Jig does the work.** When the copy running the command is older than the Jig it
   upgrades from, it hands the whole run to that newer one and says so:
   `upgrade: this jig is 0.16.1; handing the upgrade to 0.17.0 from …`. This starts with the
   release that brings it; an older copy still does the work itself.
2. **It checks that it may start, before it touches anything.** It stops, and says what to do, when:
   - you have uncommitted changes to tracked files — commit them, `git stash` them, or finish the
     task they belong to (new files git does not track yet do not count);
   - Git converts line endings here (`core.autocrlf=true`) and nothing keeps Jig's files at LF — it
     names the lines to add to `.gitattributes`;
   - you are on the branch of a started task — the upgrade would take this checkout off it. Give
     the task a worktree of its own with `jig task start <id> --worktree`, which puts this checkout
     back on your base branch, and run the upgrade again; if another session is still working on
     that task here, wait until it has finished. In the task's own worktree, run the upgrade in
     the main checkout instead. A session that only looked around (`jig status`,
     `jig task show` of another task) does not stop it;
   - `jig verify` is running in this checkout — run the upgrade when it has finished.
3. **It works on a branch of its own**, `jig/upgrade-<version>`, cut from your base branch
   (`git.base_branch`) — not from the branch you were on, so the upgrade never ends up inside a
   task's pull request.
4. **It checks the result before committing.** An install that is still missing something is not
   committed; run `jig upgrade` again on the same branch and it carries on.
5. **One commit**, titled `Upgrade Jig <from> -> <to>`, with the steps this release asks for by
   hand and a link to this page. Then it goes as far as your agent's git rights allow
   (`agent.git`): at `none` the change is staged and the run prints the one command that commits
   it; at `commit`, `push`, `pr` and `merge` it commits, pushes, opens the pull request and merges
   it once CI is green, exactly as `jig task ship` does.

It ends by saying where you are and how to get back:

```text
next: this upgrade is on branch jig/upgrade-0.17.0; once it is merged into main, merge that into the branches still in progress
next: to go back to what you were doing: `git checkout task/my-feature`
```

Branches that were already in progress get the upgrade when you merge the base branch into them.
If nothing needed changing, the run goes back to the branch you were on and removes the one it
made.

`jig upgrade --dry-run` never stops and never makes a branch — `jig status`, `jig verify` and
`jig doctor` rely on it. It prints what would stop a real run as `note: a real upgrade would stop:
…` lines instead.

Two kinds of project work differently. One that uses a single branch
(`git.branch_per_task: false`) gets the commit on the branch it is on, and nothing is pushed. One
installed with `jig init --link` — Jig's own repository — keeps upgrading in place, with no branch
and no commit.

## From 0.21.0 to 0.22.0

Nothing on the checklist the upgrade itself prints, and nothing to do by hand. The installer changed
(see below); `.ai/config.yaml` is not touched.

**Placed for you.** `jig upgrade` adds `.ai/scripts/lib/output.sh`, the shared output layer, updates
the scripts that use it (`doctor`, `upgrade`, `status`, `checkout`, `task`) and the `jig-setup` skill under
`.claude/skills/` and `.codex/skills/`.

**What you will see at a terminal.** `jig doctor`, `jig upgrade` and `jig status` print what needs you
first (failures, then warnings, each with its fix), group the rest, and end with a short summary; the
installer and `jig-setup` use the same layout, with `ask` before a question. The facts are the
same; the order, the grouping and the closing summary line are new.

**Pipes, CI and agents get the same bytes as before** from `doctor`, `upgrade`, `status` and the
installer (`jig-setup` is a skill and speaks in blocks wherever it runs). The terminal form is chosen once per run, only
when standard output is a terminal. Anything that reads the output through a pipe, a file or an
agent's shell gets the report you had in 0.21.0, byte for byte; a script that parses it keeps working.
`JIG_TERMINAL=0` asks for the plain form under a terminal and `JIG_TERMINAL=1` for the terminal form
under a pipe. `NO_COLOR` set to anything non-empty, or `TERM=dumb`, removes colour and keeps the
grouping. The PowerShell installer colours through the console, never with escape codes.

**An upgrade no longer refuses because of a session that only looked around.** In 0.21.0 an upgrade
stopped when another agent session had run any Jig command in the checkout within the last hours.
From 0.22.0 it stops only when you are on the branch of a started, unfinished task, and the message
names the task, its branch and the way on (`jig task start <id> --worktree`, then the upgrade again;
inside the task's own worktree, run it in the main checkout). This holds when the upgrade is run by
0.22.0: after `jig self-update`, or handed there by an older copy of the project's script, which
hands the run to the newer Jig. A project with `git.branch_per_task: false` is not asked at all.

**The installer changed.** `install.sh` and `install.ps1` speak the new layout at a terminal and
print what they printed before elsewhere (for `install.ps1`, held by line-level checks). If you run the installer again on a machine you keep up to
date, nothing else changes; the Windows release checklist was not walked on a real machine for this
release (see the changelog).

## From 0.20.0 to 0.21.0

Nothing on the checklist the upgrade itself prints. The installer did not change. One thing is
placed for you, two are yours to choose, and two change what Jig refuses.

**Placed for you.** `jig upgrade` adds `skills/jig-task/references/delegation.md`, updates the skills
that changed (`jig-autopilot`, `jig-implement`, `jig-review`, `jig-architecture-review`, `jig-verify`,
`jig-task`, `jig-setup`, `jig-idea`, `jig-release`) under `.claude/skills/` and `.codex/skills/`.
`.ai/config.yaml` is not touched; the comment in the template config only gains
`release.merge`.

**Finishing a task now needs its records.** From 0.21.0, `status ready`, `knowledge_consolidated true`
and `jig task ship` refuse a task whose class asks for a stage that left no record (the approved design
for T3 and T4, a review receipt for T2 and up, `status ready` before consolidation) and say which and
how to write it. A task you filed before the upgrade has no `route_evidence` key and is judged as
before: the same list is printed as a warning (`was filed before route evidence was checked, so this
passes without: ...`) and the task passes. A task filed after the upgrade is refused. Two command
forms changed for everyone, and a refusal names the new form: lowering a class is
`jig task set <id> class <Tn> --reason <text>`, and `jig task autopilot <id> resume` takes
`--answer <the human's answer>` and is refused in an unattended run. Where nobody answers (an
unattended clone), `jig task gate <id> approved` is refused and an approval is given with `--by agent`;
an attended clone is unchanged. A script or a skill of your own that calls these must use the new forms. Where a project's own tests
or smoke steps jump a fresh task to its end, classify it and sign verification off first
(`jig task set <id> class T0`, `status ready`, `knowledge_consolidated true`).

**Yours to choose: `release.merge`.** Only for a project that releases through an epic. The default,
`agent`, is the behaviour you had. To keep the merge of an epic's final pull request for yourself even
when your agent may merge tasks, `jig config set release.merge human --local`; it is personal and is
ignored in `.ai/config.yaml`. An epic already cut finishes on `finish/<id>` instead of on the epic
itself; nothing to do beforehand.

**Yours to choose: `claude.implement_model` and `claude.review_model`.** Unset by default, which keeps
every stage with your agent. To have Claude Code hand writing the code, or reviewing it, to a helper on
a cheaper model, answer the new question in `jig-setup`, or
`jig config set claude.implement_model sonnet --local` (likewise `claude.review_model`). Read
[Autopilot: helpers on another model](/autopilot#helpers-on-another-model) first.

**A link in a task workspace is checked wherever it leads.** If your `.ai/workspace` or
`.ai/workspace/tasks` is a link you made yourself to a folder outside the repository and its worktrees,
the commands that write into a task workspace now refuse it. The links `jig task start --worktree`
makes, and one from a worktree to its owner's workspace, are fine.

## From 0.19.0 to 0.20.0

Nothing on the checklist the upgrade itself prints. Two things are placed for you, two are yours to
choose, and one changes what a stale review means.

**Placed for you.** `jig upgrade` adds the `jig-release` skill (under `.claude/skills/` and
`.codex/skills/`, as for the other skills), updates the other skills that changed, and refreshes the
section between `<!-- jig:begin -->` and `<!-- jig:end -->` in your `AGENTS.md` when Jig may: it gains a
paragraph on `jig-release` and one on lean routes. `.ai/config.yaml` is not touched; the upgrade's usual
report of keys it does not mention will include `worktree.share`, and leaving it on its default (nothing
shared) is correct for most projects.

**Yours to choose: `worktree.share`.** If your project keeps separate repositories under edit in a folder
such as `packages/`, declare it in `.ai/config.yaml` and put the folder in `.gitignore`:

```yaml
worktree.share: [packages]
```

Do not also leave that folder in `worktree.carry`; if you do, it is shared and the copy is skipped with a
warning. The 0.19.0 and earlier advice to work on such packages in the main checkout no longer applies.
Worktrees that already exist are not changed; `jig task bootstrap <id>` links the shared entries into one.

**Yours to choose: `route.depth`.** The default, `full`, is the route you ran before; nothing changes
unless you set it. To take less, `jig config set route.depth lean --local`; it is personal and is
ignored in `.ai/config.yaml`. Read what lean trims first (`jig task route <id>`, or
[Concepts](/concepts)).

**A task that has already started can be given a worktree.** `jig task start <id> --worktree` on it
now moves it, instead of refusing. This does not change a task you have not started.

**Reviews in flight.** A review receipt written by 0.19.0 or earlier has no `diff` or `context`, so it is
compared by the working tree, as before, until the task is reviewed again and the receipt is rewritten.
After that, merging the base branch into a task no longer makes the review stale when nothing the task
touches moved. If a task is stale after the upgrade, the message now says whether its own change or the
knowledge under it moved.

## From 0.18.0 to 0.19.0

Nothing on the checklist the upgrade itself prints. What changes is what `jig verify` finds, and one
of your own settings gains a sibling.

**`.devcontainer/`, `.ddev/` and `.lando.yml` are no longer reasons to refuse.** The 0.18.0 section
below names them as signs Jig could not place. Now a project with `.ddev/config.yaml`,
`.lando.yml` or `.devcontainer/devcontainer.json` has its checks run in that environment, and a
stopped one is refused with its start command. Of the signs 0.18.0 listed, only a `.devcontainer/` or `.ddev/` folder without its
manifest, services mounting the project that Jig cannot pick one of, or a `DB_HOST` naming a compose
service still stop `jig verify` with exit 3; a stopped environment is refused too, with its start
command. The DDEV, Lando and devcontainer detectors have been tried with stand-ins for
their commands only; if one misreads your setup, `jig config set run.exec <command> --local` overrides
it, and `jig verify --explain` shows where the checks go.

**A Devilbox or Laravel Herd project may now run somewhere new.** A project served by Devilbox (its PHP
container mounts your project, wherever its data folder lives) has its checks run in that container; a
Herd site runs them on this machine with Herd's PHP first on `PATH`. Neither needs a setting. If
Herd's PHP is not the one you want, or Jig did not find it, name the folder yourself:

```bash
jig config set run.path "/Users/me/Library/Application Support/Herd/bin" --local
```

**The other nine profiles now run in the environment instead of being skipped.** In 0.18.0, inside a
container the `shell`, `python`, `go`, `rust`, `ruby`, `jvm`, `dotnet`, `dart` and `swift` profiles were skipped
with a reason; now they run there, so a check that was reported as skipped may now run, and fail. Under an
environment, Python's tools come from a `.venv/` or `venv/` that runs there, otherwise from the
environment's own `PATH`, not from the virtualenv of this machine.

**`jig doctor` and `jig verify --explain` may now warn.** When the checks run on this machine, they
compare its PHP, Node and Python with `composer.json`, `package.json` (`engines.node`) and
`.python-version`. A warning is advice only; nothing is refused because of it.

**`jig task start` and `jig upgrade` no longer suggest deleting a session's record.** The refusals name a
worktree or waiting; the record expires on its own after `checkout.busy_ttl`. A session that only filed
tasks no longer occupies the checkout.

## From 0.17.1 to 0.18.0

Nothing on the checklist the upgrade itself prints. Two things about running Jig change, and one is unchanged.

**If your project runs in a container, `jig verify` may now refuse, where it used to run on this
machine.** On Laravel Sail, or with one docker compose service that mounts the project, Jig finds the
container and runs the checks in it; `jig verify --explain` prints where. If there are signs of a
container it cannot place — a `.devcontainer/`, `.ddev/` or `.lando.yml`, two services mounting the
project, a `DB_HOST` in `.env` that names a compose service — it exits 3 with the reason. Say *"set
up Jig for me"* (`jig-setup` now asks where your tests run) or set it yourself, in your own
`.ai/config.local.yaml`:

```bash
jig config set run.exec "docker compose exec -T -w /app app" --local   # the command that reaches the container
jig config set run.exec host --local                                   # this machine is right after all
```

A stopped container is refused too, with the command that starts it where Jig knows one. In a
task's worktree, a container that mounts another copy of the project is refused: start an
environment for the worktree. Projects that need none of this see no change; with `CI` set and
`run.exec` at `auto`, nothing is detected or refused.

**`jig task start` now refuses a checkout another session is working in.** Where it used to move
HEAD under that session, it stops, names the task or session and how long ago it ran, and offers
`jig task start <id> --worktree`, waiting, or deleting the stale record it names. Start the task in a
worktree, or finish the other work first.

**Leftover temporary files from older versions stay.** Jig no longer leaves `*.tmp.<pid>` files
behind when a command is interrupted, but the ones an earlier version already left are not removed.
They are files named like a real file followed by `.tmp.` and a number (`.new.`, `.join.` and
`.restore.` too); nothing reads them, so delete them once, with no Jig command running.

Unchanged: `jig task set <id> status consolidated` still refuses until the task's pull request has
merged, as it has since 0.17.0.

## From 0.16.1 to 0.17.0

Nothing on the checklist the upgrade itself prints — that only names steps from 0.15.0 and older,
and you are already past them. Two things about running the upgrade change anyway.

**`jig upgrade` now refuses a dirty working tree, where it used to run regardless.** If you are in
the habit of running it with edits still uncommitted, commit or `git stash` them first, or finish
the task that owns them; the upgrade tells you which when it refuses. It also stops if another
session or a `jig verify` run is busy in the same checkout — wait for it to finish, or the message
names the record to remove if that session has already ended.

**It now works on its own branch, `jig/upgrade-0.17.0`, and makes one commit.** You no longer
apply the upgrade's changes to whatever branch you happened to be on: it cuts its branch from your
base branch, commits there, and — depending on your agent's git rights — pushes, opens a pull
request and merges it, the same as `jig task ship`. See
[An upgrade is a change of its own](#an-upgrade-is-a-change-of-its-own). Once that branch is
merged, merge the base into any branch still in progress, the way the upgrade's own closing lines
say.

**If you worked around the Windows line-endings fault by hand, the workaround is now redundant.**
A project that added `.ai/** text eol=lf` (and the two skills lines) to `.gitattributes` to fix
[the known issue](/known-issues) keeps working; the upgrade now ships the same pinning, scoped
more precisely to what Jig places (`.ai/manifest`, `.ai/scripts/**`, `.ai/profiles/**`,
`.ai/templates/**`, both adapters' skill directories), for projects that never added it themselves.
Nothing to reconcile either way.

## From 0.16.0 to 0.16.1

Nothing to do by hand if you upgrade the way the top of this page shows: `jig self-update`, then
`jig upgrade` in the project. The `jig` on your machine is then 0.16.1, and it does the work itself.

Two kinds of project need a step more when the upgrade is run by the project's own copy instead —
`.ai/scripts/jig upgrade`, which is how an agent usually runs it. That copy is the version you are
leaving, and in these two it hashes Jig's files differently from 0.16.1.

**A repository with SHA-256 object names** (created with `git init --object-format=sha256`).
Straight after the upgrade, `jig status` reports every framework file as modified — measured on a
project of 97 framework files:

```text
drift: 97 modified, 0 missing, 0 pending
```

Nothing is wrong with the files. Run the upgrade once more: this time 0.16.1 does the work, records
the files as they are, and the drift goes.

```bash
.ai/scripts/jig upgrade
jig status     # drift: 0 modified
```

**A repository whose clean filters cover Jig's own scripts** — a `filter=` line in
`.gitattributes` matching `*.sh`, say — when an earlier upgrade already left those scripts
reported as modified. The project's copy cannot replace them, itself included, so however often it
runs it ends like this, and `jig version` stays at 0.16.0:

```text
jig upgrade: 0 placed, 97 kept, 0 conflict(s); manifest unchanged
```

Run the upgrade with the `jig` on your machine instead; it places them, and `jig status` reports no
drift afterwards:

```bash
jig self-update
jig upgrade
```

An ordinary repository sees neither. Coming from 0.15.0 or older, you run the upgrade a second time
anyway, for the reason given [above](#what-the-upgrade-does-and-what-it-leaves-alone), and in a
SHA-256 repository that second run clears the drift too.

## From 0.15 to 0.16

This release has three steps that only you can take. None of them happens automatically, and the
first two change whether Jig keeps working the way you expect. See the
[changelog](/changelog) for everything else in the release.

<Steps>
  <Step title="Run the jig-init skill, so upgrades can reach your AGENTS.md">
    Ask your agent to run the `jig-init` skill. It adds the markers and records Jig's claim to that
    section, with your consent, and from then on improvements to Jig's own instructions arrive with
    each upgrade.

    Adding the markers by hand does **not** do it: without the recorded claim, `jig upgrade`
    reports `keep-unmarked AGENTS.md` and changes nothing, however well-formed your markers are.

    If your Jig section has also drifted from Jig's own text, markers alone are still not enough —
    no claim gets recorded, and the upgrade reports `keep-modified` instead. Reconcile the text
    first, against `.ai/templates/AGENTS.md`, and then mark it.
  </Step>

  <Step title="Install the tools your project's checks need">
    `jig verify` used to answer `ok` when a profile for your stack was active and every one of its
    checks had been skipped for a missing tool. It now refuses — exit 3, *nothing was checked, so
    this is not a pass* — and `jig task ship` will not ship on it.

    `jig verify --list` shows which profiles are installed; install what they need. If your project
    is covered by no profile at all, nothing changes for you: Jig says so plainly and does not
    block you, because there is nothing you could install to resolve it.
  </Step>

  <Step title="If you wrote a profile that checks nothing by design, say so">
    A profile that asserts nothing about the code — one that exists to carry shared setup, say —
    needs `verifies: nothing` in its `profile.yaml`. Absence means the profile claims it verifies
    something, which is the cautious default: without the line, the day its tool goes missing it
    refuses rather than quietly reporting that nothing checks your project.

    This applies only to profiles you wrote yourself. Every profile Jig ships already declares it.
  </Step>
</Steps>

## Checking that it took

Three commands answer it, and you do not need to remember which does what — run `jig doctor` first
and follow what it says.

```bash
jig doctor
```

The lines to look for:

```text
ok    instructions (claude): Jig section present and kept current
ok    config keys: 2 not mentioned in .ai/config.yaml, each on its default: worktree.carry, checkout.busy_ttl (jig config keys)
```

A `warn` reading `Jig section in AGENTS.md is not marked, so upgrades cannot reach it` means step
one is still outstanding. One reading `no Jig section in AGENTS.md` means Jig's instructions never
reached your agent at all, which is worth fixing before anything else.

One line deserves a second look because it is reported as **ok** rather than a warning:

```text
ok    instructions (claude): Jig section changed here; upgrades keep your text
```

That is not a problem — it is Jig respecting an edit someone made inside the markers — but it does
mean this project will not receive improvements to that section. If the edit was deliberate, leave
it. If nobody remembers making it, reconcile against `.ai/templates/AGENTS.md`.

```bash
jig config keys
```

Lists every setting this version reads, its default, and where its current value comes from — your
project's file, your personal one, or the default. Use it after reading the upgrade's closing line,
to see what the new version brought.

```bash
jig verify
```

The one that proves step two. A pass means checks ran. `nothing was checked, so this is not a pass`
with exit 3 means tools are still missing. `nothing here checks this project` with exit 0 means no
profile covers your stack — not something an upgrade can fix, and not something that blocks you.
Run `jig verify --explain` first if you want to see what a run will expand to before spending the
time on it.
